# Дасан зохицох (эрт зогсох) self-consistency — офлайн симуляци

**Асуудал.** 8 хувилбар + санал хураалттай (E2/E4) нэг асуултын хугацаа p50 ≈ 72 с, p95 ≈ 348 с; нэг
хувилбартай (E1/H4) ≈ 8 с. **Зорилго.** Adaptive-Consistency (Aggarwal et al., 2023) ба ESC
(“Escape Sky-high Cost”, Li et al., 2024)-ийн загвараар хувилбарыг давалгаагаар үүсгэж, санал хангалттай
нийлмэгц зогсоох нь EX-ийг хэр хадгалж, зардлыг хэр бууруулахыг шинэ үүсгэлтгүйгээр, зөвхөн dev-ийн бэлэн
run дээр үнэлэх.

* Код: `src/mn_text2sql/eval/adaptive.py` (симулятор + онлайн зогсоох дүрэм), тест: `tests/test_adaptive.py`.
* Ажиллуулах: `PYTHONPATH=src python -m mn_text2sql.eval.adaptive --perms 200 --runs E4 E5h_w1`
  (DB, GPU, загвар шаардлагагүй; зөвхөн `results/runs/dev/*`).

## 1. Хувилбар хэрхэн үүсдэг вэ (код уншсан дүгнэлт)

* `Pipeline.generate` (pipeline/orchestrator.py): omnisql/generic гэр бүлд **нэг** vLLM дуудлага
  `llm.chat(messages, n=8, temperature=0.8)` — 8 түүвэр нэг batch-аар (prefix caching-тэй) зэрэг үүснэ
  (`llm/client.py`: OpenAI-compatible body-д `"n": n`). sqrl гэр бүл л 8 thread-ээр agent ажиллуулна.
* Дараа нь 8 хувилбарыг **дараалан** `_single_turn`-аар боловсруулна: SQL гүйцэтгэх, алдаа/хоосон бол
  `repair_rounds=2` хүртэл тус бүр нь **тусдаа, дараалсан** LLM дуудлагаар засуулна. Иймээс сүүлийн (p95)
  хугацааг үүсгэлтээс илүү дараалсан засварууд нэмдэг.
* Хувилбарууд i.i.d. түүвэр тул аль ч k ширхэг дэд олонлог нь `n=k` үүсгэлттэй статистикийн хувьд ижил —
  тиймээс бэлэн 8 хувилбарын дараалал (эх ба 200 санамсаргүй сэлгэмэл) дээр симуляци хийх нь зөв.
* **Хугацааны гол олдвор.** E1 (n=1) ба E2 (n=8) хоёулаа `workers=8` зэрэг асуулттай ажилласан:
  E1-д GPU дээр ~8 дараалал, E2-т ~64 дараалал зэрэг явсан (E2-ийн нэгж дарааллын хурд ~11 ток/с,
  E1-д ~51 ток/с; completion токен 8.2 дахин). Өөрөөр хэлбэл **72 с нь ачаалалтай eval-ийн тоо**;
  ганц хэрэглэгчтэй үйлчилгээнд n=8-ийн нэг batch нь ойролцоогоор E1/H4-ийн хугацаатай (≈8–15 с) тэнцэнэ.

## 2. Арга

**Өгөгдөл.** `results/runs/dev/E4` (E2-ийн 8 хувилбар + vote_filter + дүрэм; 300 асуулт, 224 хариулах
боломжтой) ба `E5h_w1` (E4 + H4-ийн greedy хувилбар эхэнд, 1 санал). Мөр бүрийн `cand_hashes`,
`cand_correct`, `status`, `result_hash`, `gen_ms`, `latency_ms`.

**Санал хураалт** нь `Pipeline.vote`-той ижил: алдаатай (hash-гүй) хувилбарыг хасна, тэнцвэл эхэлж гарсан
нь. **vote_filter**: degenerate/DB-д байхгүй утгатай хувилбарыг мөрөнд тусад нь хадгалаагүй тул run-ын
бодит сонголтоос сэргээсэн — шүүлтгүй олонх нь сонгогдсоноос дээгүүр жагссан hash бүрийг «муу» гэж
тэмдэглэв (abstained бол бүх hash). Энэ нь доод хязгаар боловч k=8, эх дараалалд E4 ба E5h_w1-ийн
`correct`-ыг **300/300** яг давтана. Сонгогдсон hash «муу» эсвэл бүх хувилбар алдаатай → татгалзана
(онлайн `abstain_on_error`/vote_filter-тэй адил).

**Тогтмол барьсан.** intent_check/дүрмээр `refused`/`clarify` болсон асуулт (E4: 38) — симуляцид
статус өөрчлөгдөхгүй, зардлын статистикт ороогүй (онлайнд дүрэм үүсгэлтээс өмнө ажилладаг).
Зардлыг үүсгэлт хийгдсэн 262 асуулт дээр тооцов.

**Хэмжүүр.** EX_ans — 224 хариулах боломжтой асуултын EX (эх дараалал ба 200 сэлгэмэлийн μ±σ);
EX_нийт — runner-ийн нийт зөвтэй ижил дүрмээр (`score_answer`: хариулах боломжгүйд татгалзах/тодруулах, хоёрдмолд
тодруулах эсвэл тайлбартай таарсан SQL)/300; μN, p95N — үүсгэсэн хувилбарын тоо. 2026-10-31-нд засав: өмнө нь
хоёрдмол асуултын тайлбартай таарсан хариултыг тооцдоггүй байсан тул EX_нийт ~4 хувиар бага гарч байв (симуляторын
fixed8 нь одоо бодит E4-ийн 53.00, E5h_w1-ийн 53.33-тай яг таарна). EX_ans өөрчлөгдөөгүй.

**Хугацааны таамаг (хоёр хувилбар).**
* **A — ачаалалтай сервер** (eval шиг 8 зэрэг асуулт, GPU throughput-оор хязгаарлагдана): хугацаа
  токентой пропорциональ, `ovh + gen_E2 · n/8` (ovh = latency − gen; засварын хугацаа gen-д орсон).
* **B — ганц хэрэглэгч**, давалгаанууд дараалсан: давалгаа = `T1·(1 + α(w−1))`, T1 = H4-ийн gen_ms
  (≈8 дараалал зэрэг), α = 0.1 (w түүврийн хамгийн урт нь дунджаас урт). Хувилбар бүрийн дараалсан
  засвар B-д ороогүй тул p95-ыг доогуур үнэлнэ.

**Бодлого.** (a) тогтмол k = 1…8; (b) `agree m`: эхний m хувилбар бүгд нэг үр дүнтэй бол зогсох, эс бөгөөс
үлдсэнийг нэг давалгаагаар (m = 2, 3); (c) `beta C`: тэргүүлэгч a, хоёрдугаар b санал — Beta(a+1, b+1)-ийн
P(p₁ > p₂) ≥ C бол зогсох (Adaptive-Consistency; шилдэг 2-ын хувьд Dirichlet-ийн хялбаршуулга),
C ∈ {0.7, 0.8, 0.9, 0.95}; (d) давалгааны хэмжээ w ∈ {1, 2, 4} (vLLM `n=w`), мөн ESC (сүүлийн давалгааны бүх
түүвэр ижил бол зогсох). `g+` = эхэнд нэг greedy хувилбар (E5h).

Beta шалгуурын жишээ: (2,0) → 0.875, (3,1) → 0.8125, (2,1) → 0.6875. Тиймээс `beta 0.8 w4` нь
«эхний 4-өөс ≥3 нь нийлсэн (эсвэл 2 нийлж бусад нь алдаатай) бол зогс, эс бөгөөс дахин 4».

## 4. Дүгнэлт

1. **Хэмнэлт хязгаарлагдмал.** 262 асуултын зөвхөн 49 нь 8/8 санал нэгтэй; тэргүүлэгчийн медиан 4/8.
   Иймээс EX-ийг хадгалах дүрэм (beta ≥ 0.8) дунджаар 1.7–3 хувилбар л хэмнэнэ (−20…−37%).
2. **Санал болгох: `beta:0.8:w4`** (4 + 4 хоёр давалгаа). EX_ans fixed8-тай бараг ижил (μ 47.04 vs 47.06,
   −0.02 pp; эх дараалалд −0.45 pp = 1 асуулт), EX_нийт 52.60 vs 52.62; үүсгэлт **−21%** (8 → 6.29;
   асуултын ~46% нь 4-өөр зогсоно), ачаалалтай сервер дээр p50 **73 → 57 с (−22%)**, GPU-ийн
   throughput ~1.27×. Илүү хямд хувилбар: `beta:0.8:w2` (−36% хувилбар, A p50 38 с) — EX −0.37 pp.
3. **Greedy-эх** (`g+beta:0.8:w4`): E4 fixed8-аас +1.0 pp (48.06 vs 47.06) бөгөөд 12% цөөн үүсгэлт (7.03 vs 8);
   E5h_w1-ийн бүрэн 9-өөс −0.06 pp, −22% үүсгэлт. Гэхдээ E5h-ийн өсөлт өөрөө dev дээр сонгогдсон тул
   test дээр дахин шалгах хэрэгтэй.
4. **p95 бараг буурахгүй** (348 → 343 с): удаан асуултууд санал зөрдөг (бүгд 8 хүртэл үүсгэнэ) бөгөөд
   хугацааг дараалсан засварууд эзэлдэг. p95-ын жинхэнэ шийдэл — хувилбар бүрийн `_single_turn`
   засварыг зэрэг (ThreadPool) ажиллуулах, эсвэл засварыг зөвхөн сонгогдсон хувилбарт хийх.
5. **Ганц хэрэглэгчтэй үед** n=8 нэг batch бараг «үнэгүй» (санах ойн зурвасаар хязгаарлагддаг decode);
   давалгаа нь дараалсан тул эрт зогсолт хугацааг **нэмэгдүүлнэ** (B: 13.3 → 16.8 с). Иймээс дасан
   зохицох дүрэм нь **олон хэрэглэгчтэй / ачаалалтай** үед GPU зардал ба хугацааг бууруулах арга;
   демо (нэг хэрэглэгч) үед `candidates=8`-ыг нэг batch-аар үлдээх нь зөв.

## 5. Онлайн холболт (анхдагчаар унтраалттай)

* `RunOptions.adaptive_stop: str | None = None` (`_LATE_DEFAULTS`-д бүртгэсэн тул хуучин run-ын
  fingerprint өөрчлөгдөхгүй); flow builder-ийн «Санал хураалт» node-д `str?` талбар.
* `Pipeline.generate`: `adaptive_stop` өгөгдсөн ба `candidates > 1` үед `_generate_adaptive` —
  давалгаа бүрт `llm.chat(n=w)` (давалгаа бүрт өөр seed: ижил seed-тэй n=w дуудлага ижил түүвэр буцаана),
  `AdaptiveStopper.done` (vote_filter асаалттай бол degenerate/буруу утгатайг тоолохгүй) биелбэл зогсоно.
  `g+` угтвар — эхэнд temperature 0-ийн нэг хувилбар. Санал хураалт, `_finish` өөрчлөгдөөгүй.
* Утга: `beta:0.8:w4` (санал болгох), `g+beta:0.8:w4`, `beta:0.8:w2`, `agree:2`, `esc:w4`, `fixed:4`.
  Жишээ: `--set adaptive_stop=beta:0.8:w4`.
* Анхаарах: (1) `confidence = best_n / len(cands)` нь үүсгэсэн тоонд хуваагдана — `abstain_threshold`
  ашигладаг тохиргоонд босгыг дахин тааруулах; (2) эрт зогссон асуулт 4 хувилбартай тул I-бүлгийн
  `clarify` шийдвэр өөр тархалттай болно; (3) онлайн туршилт (Kaggle/L4) хийгдээгүй — симуляцийн тоо.

## 6. Хязгаарлалт

* vote_filter-ийн «муу» hash нь доод хязгаар (сонголтоос доогуур жагссан муу hash мэдэгдэхгүй) —
  жижиг k-д EX-ийг бага зэрэг өөдрөг үнэлж магадгүй.
* Хугацааны загвар токен ≈ хувилбарын тоо гэж үздэг (хувилбар бүрийн токен, засварын тоо мөрөнд байхгүй).
* Зөвхөн dev (300); test-ийг уншаагүй.

## 7. Зэрэгцээ засвар (`repair_workers`)

* **Код.** `Pipeline._repair_chains` (pipeline/orchestrator.py): хувилбар бүрийн `_single_turn` (гүйцэтгэл +
  ≤ `repair_rounds` засвар) нэг «гинж». `repair_workers=1` (анхдагч) — хуучин дараалсан давталт, byte-ижил.
  `> 1` — гинж бүр дотроо дараалсан, гинжүүд хязгаартай `ThreadPoolExecutor`-оор зэрэг; үр дүн хувилбарын
  анхны дарааллаар буцаж, санал хураалт ба тэнцээг шийдэх дүрэм өөрчлөгдөхгүй. `adaptive_stop`-ийн давалгаа
  бүрт мөн хэрэглэгдэнэ. Flow builder-т «Алдаагаар засах (E1)» node-ийн талбар.
* **Хуваалцсан төлөв (шалгасан).** `Executor` — `ThreadedConnectionPool` + semaphore, дуудлага бүр pool-оос
  тусдаа psycopg2 холболт авна (maxconn 16 ≥ workers); `httpx.Client` thread-safe, токены тоолуур lock-той;
  залхуу кэш (`bool_cols`, postproc, LiteralChecker) зэрэгцээ эхлэхээс өмнө үндсэн thread-д үүсгэнэ;
  Studio-гийн явцын callback thread-local тул ажлын thread бүрт дамжуулна; `agent_log` нь хувилбар тус бүрийн
  объект (хуваалцаагүй).
* **Алдааны тусгаарлалт.** Засварын LLM дуудлагын алдаа өмнө нь ч `_single_turn`-д баригддаг (өмнөх хувилбар
  үлдэнэ). Зэрэгцээ горимд гинжний бусад алдаа (DB холболт тасрах г.м.) тухайн хувилбарыг `error_stage="llm"`
  болгоод бусад гинж үргэлжилнэ (дараалсан горимд хуучин шигээ дээш гарна). Хугацааны хязгаар гинж бүрт
  тусдаа: LLM-ийн `timeout_s`, DB-ийн `statement_timeout`.
* **Хүлээгдэх p95 нөлөө (ҮНЭЛГЭЭ, хэмжээгүй).** Санал зөрдөг удаан асуултад жишээ нь 4–5 хувилбар 2 удаа
  засагдвал дараалсан засвар ≈ 8–10 LLM дуудлага; 4 thread-тэй бол ≈ 2–4 дуудлагын хугацаа (vLLM зэрэг
  хүсэлтийг batch-лана, 7B загварт жижиг batch бараг шугаман). Иймээс p95 ≈ 343–348 с → ойролцоогоор
  150–200 с болно гэж тооцож байна; vLLM-ийн KV-cache/GPU дүүргэлтээс хамаарна — Kaggle/L4 дээр хэмжих хэрэгтэй.
* **Санал болгох тохиргоо.** Studio (вэб, санал хураалтын node-той, 8 хувилбар, vLLM): `repair_workers=4`.
  `WEB` (1 хувилбар) — нөлөөгүй (нэг гинж). CPU/LM Studio шиг хүсэлтийг дараалуулдаг серверт 1–2.
  Eval run-д анхдагч `1` хэвээр.
* **Eval үр дүнд нөлөөгүй.** `repair_workers` нь `_LATE_DEFAULTS`-д (1) — анхдагч утгатай бол fingerprint/run
  hash өөрчлөгдөхгүй, гаралт byte-ижил. `> 1` болговол hash өөрчлөгдөнө; логик нь ижил (tests/test_parallel_repair.py:
  ижил SQL, дараалал, санал) ч vLLM-ийн batch-ийн хөвөгч таслалын тодорхой бус байдлаас засварын токен
  ховор зөрж болзошгүй тул тайлангийн тоонд ашиглахгүй.
