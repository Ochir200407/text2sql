# Agentic урсгал (G бүлэг)

Код: `src/mn_text2sql/pipeline/agent.py`. Тохиргоо: `config/experiments.yaml` → `agent*` талбарууд, G1–G4.

Энэ нь туршилтын төлөвлөгөөнөөс (A1–F10) гадуурх нэмэлт. Санаа нь text2sql-thesis-ийн Planner → Writer → Critic
агентаас гаралтай. Харин энэ систем guard, read-only executor, retrieval, загвар бүрийн протокол дээр ажилладаг.

## Алхам

```
асуулт → (RAG контекст) → [plan] → write (загварын протокол, E1 засвар, E2 санал хураалт)
       → observe: гүйцэтгэл + литерал tool → [critic] → олдвор/санал байвал revise → … (≤ agent_rounds)
```

| Алхам | LLM? | Юу хийх | Тохиргоо |
|---|---|---|---|
| plan | тийм | Хүснэгт, join, шүүлт, агрегат, эрэмбэ, гаралтын баганын англи товч төлөвлөгөө гаргана. SQL бичсэн бол хасна. Төлөвлөгөө writer-ийн evidence-д орно | `agent_plan` (G3) |
| write | тийм | Загварын өөрийн протокол: Arctic → OmniSQL prompt + `<think>`, sqrl → `<sql>`/`<answer>` судлах алхмууд | — |
| observe | **үгүй** | Гүйцэтгэлийн алдааг шалгана — хатуу олдвор, заавал засуулна. Хоосон үр дүн / бүгд NULL нь зөөлөн олдвор: зөв хариу хоосон байж болох тул critic-д л дамжина, critic REVISE гэвэл засна. **Литерал tool** (зөвхөн текст баганад; `lower()`/`ILIKE` бол том жижиг үсэг ялгахгүй): `col = '…'`, `IN (…)`, `LIKE '…'` дахь текст утга тухайн баганад байгаа эсэхийг DB-ээс шалгана. Байхгүй бол тухайн баганын хамгийн ойр (ILIKE) эсвэл хамгийн түгээмэл хадгалсан утгуудыг санал болгоно. Хувийн мэдээллийн (pii) баганад утга харуулахгүй. Хатуу олдвор зөвхөн үр дүн хоосон үед; IN жагсаалтын аль нэг утга байвал зөөлөн | `agent_literal_check` |
| critic | тийм | Асуулт, SQL, үр дүнгийн 8 мөр, tool-ийн олдворыг өгнө. Загвар `VERDICT: OK` эсвэл `VERDICT: REVISE - …` гэж хариулна. VERDICT мөр байхгүй бол `UNPARSED`, LLM-ийн алдаа бол `ERROR` гэж тэмдэглэнэ. Хоёулаа OK шиг (SQL өөрчлөхгүй). Critic-ийн формат дагалтыг `agent_log`-оос хэмжинэ. `<think>`-ийг хасна; токены хязгаар = загварын `max_tokens`. Сүүлийн тойрогт critic дуудагдахгүй | `agent_critic` |
| revise | тийм | Олдвор ба санал writer-ийн яриа руу нэмэгдэнэ. Arctic-ийн хувьд: өмнөх хариу + «Review of your query», sqrl-ийн хувьд: `<observation>` | `agent_rounds` (анхдагч 2) |

Хамгаалалт:
- **Татгалзалтыг хүндэтгэнэ.** Загвар SQL-гүй бүрэн хариу өгвөл (`error_stage = refusal`, status `refused`) agent ба E1
  SQL бичүүлэх гэж шахахгүй — TrustSQL-ийн татгалзалтыг хадгална. Тасарсан/SQL олдоогүй гаралт (`extract`) нь форматын
  алдаа бөгөөд үүнийг E1-ийн засвар хариуцна (agent засуулахгүй).
- **Муу засварыг үгүйсгэнэ.** Засвар гүйцэтгэгдэхгүй, эсвэл ажиллаж байсан үр дүнг хоосон болговол өмнөх хувилбар хадгалагдаж,
  давталт зогсоно. Энэ нь бичлэгийн `agent_log`-д `accepted: false` гэж тэмдэглэгдэнэ.
- **SQL-ийн хамгаалалт.** Загварын бүх SQL guard → read-only executor-оор дамжина. Литерал tool-ийн асуулга guard-аар дамжихгүй.
  Эдгээрийг кодоос бүрдүүлдэг: semantic model-д бүртгэлтэй хүснэгт ба текст баганын нэр, `''` escape хийсэн утга
  (standard_conforming_strings). Bot role нь read-only.
- **Засварын дараах итгэл.** E2 + agent үед засварласан SQL-ийн үр дүнг дэмжсэн хувилбаруудын хувиар итгэлийг дахин
  тооцно. Иймээс E3-ийн босго хариулж буй SQL-д хамаарна.
- **Яриаг үргэлжлүүлэх.** Revise нь E1-ийн засварын бүрэн яриаг (system, схем, асуулт, prefill) үргэлжлүүлнэ. sqrl revise-д
  `<sql>` судлах алхмыг (≤ 2) гүйцэтгэнэ; `<answer>` гаргаагүй бол засварыг үгүйсгэнэ.
- **Алдаа.** Planner/critic-ийн LLM алдаа нь асуултыг унагахгүй: төлөвлөгөөгүй / `ERROR` verdict-тэй үргэлжилнэ.
- **E2-тэй хамт.** Agent зөвхөн санал хураалтаар сонгогдсон хувилбар дээр ажиллана (8 хувилбар бүрийг биш). Итгэл
  (confidence) нь санал хураалтынх хэвээр.
- **Critic-ийн загвар.** Анхдагчаар critic ба planner нь writer-тай ижил загвар (self-critique). L4 дээр хоёр загвар
  багтахгүй. `agent_llm: qwen3.5-9b` + `T2S_AGENT_BASE_URL` тохируулбал өөр загвар (өөр GPU/порт) ашиглана.

## Туршилт (нэг удаад нэг өөрчлөлт)

| ID | Суурь | Өөрчлөлт | Юуг хэмжих |
|---|---|---|---|
| G1 | `best_config` | agent (tool + critic, ≤2 засвар) | Agent давталтын нийт нөлөө (vs best_config) |
| G2 | G1 | − critic | LLM critic-ийн нэмэр (G1 − G2) |
| G3 | G1 | + planner | Thesis-ийн Planner-ийн нэмэр (G3 − G1) |
| G4 | `best_a` | agent, RAG-гүй | RAG-гүй үед agent хэр нөхөх вэ (vs best_a, vs B5) |
| G5 | G1 | − литерал tool | Утга шалгах DB tool-ийн нэмэр (G1 − G5) |
| G6 | G2 | − литерал tool | Зөвхөн гүйцэтгэлийн алдаагаар нэмэлт засвар: «agent-гүй давталт»-ын суурь (G1 − G6 = tool + critic) |

`best_config` нь A–D-ийн шилдэг (жишээ нь B5 эсвэл D1). E1-ийг өгч болохгүй: E1-ийн суурь нь өөрөө `best_config` тул давталт
болно. G1-ийг E1-тэй (ижил суурь + засвар) харьцуулна. Adapter-тай `best_config` (D1) үед G бүлэгт LoRA асаалттай байх
ёстой (`LORA=...`; docs/SERVER.md).

```bash
STAGE=G BEST_A=A6 BEST_CONFIG=D1 bash scripts/server/run_plan_l4.sh          # G1–G6, хоёр загвар
bash scripts/server/run_experiments.sh G1,G2 arctic-r1-7b                     # гараар
```

Бичлэг бүрд `agent_log` (алхам бүрийн SQL, олдвор, verdict, засвар хүлээн авсан эсэх) ба `agent_ms` хадгалагдана.

**Анхаарах.** Agent нь асуулт бүрт 1–5 нэмэлт LLM дуудлага хийдэг. p95 latency-ийн төсвийг (30 с, L4) шалгана.

## K бүлэг — одоогийн шилдэг тохиргоон дээр (2026-10-20)

G1–G6 нь хуучин `best_config` (B5/D1) дээр тодорхойлогдсон бөгөөд хэзээ ч ажиллаагүй. Одоогийн шилдэг inference нь
I3t2 (D2 + англи prompt + T2 орчуулга + жишээний сан, 1 хувилбар) тул agent-ийг түүн дээр хэмжинэ:

| ID | Суурь | Өөрчлөлт | Юуг хэмжих |
|---|---|---|---|
| K1 | I3t2 | agent (tool + critic, ≤2 засвар) | Agent-ийн нийт нөлөө (K1 vs I3t2, McNemar) |
| K2 | K1 | − critic | Critic-ийн нэмэр (K1 − K2); K2 ≥ K1 бол critic-гүй хувилбарыг сонгоно |
| K3 | K1 | + planner | Planner-ийн нэмэр (K3 − K1) |
| WEBA | WEB | agent | Вэб үйлчилгээнд (config/web.yaml → `run_id: WEBA`) |

Critic нь англи асуултыг (en_prompt) харна. Ажиллуулах (Kaggle 2×T4, STAGE=t2-ийн дараа ижил сессэд):

```bash
STAGE=agent bash scripts/server/run_plan_l4.sh                     # K1, K2 dev
STAGE=agent AGENT_IDS="K3" AGENT_TEST=K1 bash scripts/server/run_plan_l4.sh   # K3 dev + шилдэгийг test-д нэг удаа
```

## Хязгаарлалт

- **Critic-ийн найдвартай байдал.** 7–9B загварын self-critique чимээтэй: зөв SQL-ийг «REVISE» гэж эвдэх эрсдэлтэй. G2-тэй харьцуулж хэмжинэ;
  хамгаалалт нь зөвхөн «гүйцэтгэгдэхгүй / хоосон болсон» засварыг л барина.
- **Литерал tool-ийн хамрах хүрээ.** Зөвхөн текст тэнцүү/LIKE/IN-ийг шалгадаг. Огнооны хил, нэгжийн алдааг барихгүй (critic-ийн ажил).
- **sqrl.** sqrl өөрөө `<sql>`-ээр DB судалдаг. Agent нь үүний дээр эцсийн хариуны шалгалт нэмнэ.

## Flow builder (вэб, 2026-10-25)

`/builder` (вэб үйлчилгээ) эсвэл локалд `t2s flow-ui` → http://127.0.0.1:8090/builder. Pipeline-ийн алхам бүр node:
Асуулт → Intent → Дүрэм (E4) → Орчуулга → Retrieval → Schema linking → Planner → SQL бичигч → Засвар (E1) → Санал хураалт
(E2) → Agent tool → Critic → postproc → Хариулт. Нээгдэхэд одоогийн систем (I3t2) угсарсан байна; дээд товчоор I3tr, K1,
WEB-ийг ачаална. Node нэмэх/хасах, параметр засах бүрд experiments.yaml-ийн мөр (суурийн ялгаа) ба `t2s eval` команд
шууд гарна; «Хадгалах» → `config/flows.yaml` (load_experiments нэгтгэнэ, `t2s eval --run <ID>` ажиллана). Загвартай
сервер дээр «Ажиллуулах» нь нэг асуултыг алхам бүрийн үр дүнтэйгээр (орчуулга, жишээ, хувилбар, agent-ийн олдвор/verdict,
эцсийн SQL, мөр) node-ийн доор харуулна. Код: `service/flow.py`, `service/static/builder.html`, тест `tests/test_flow.py`
(79 тохиргоо бүгд flow → тохиргоо хоёр тийш яг сэргэнэ; I3t2 + tool + critic = K1).
