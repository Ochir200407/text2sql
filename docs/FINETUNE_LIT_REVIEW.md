# Arctic-ийг санхүүгийн «тогтмол» мэдлэг ба DB бүтцээр fine-tune хийх — 4 өгүүллийн дэлгэрэнгүй уншлага (2026-10-27)

Асуулт (хэрэглэгч): «Arctic дээр санхүүгийн хэзээ ч өөрчлөгдөхгүй дүрэм журам болон DB бүтцээр fine-tune хийх — хэр нөлөөтэй вэ».

## 1. Ovadia нар, «Fine-Tuning or Retrieval?», EMNLP 2024 (arXiv 2312.05934)
- Загвар: Llama2-7B, Mistral-7B, Orca2-7B. RAG: bge-large-en + FAISS, Wikipedia.
- Fine-tune: **хяналтгүй** (дараагийн токен таах, 256 токен chunk, ≤5 эпох) — асуулт-хариултын SFT биш.
- MMLU-ийн 5 сэдэв (байгаа мэдлэг): RAG бараг бүх мөрөнд суурь болон FT-ээс илүү; FT заримдаа суурьнаас доор. Жишээ: Mistral Anatomy 0.556 → RAG 0.681, FT 0.570.
- Шинэ мэдлэг (2023-08–11 АНУ-ын үйл явдал, 910 асуулт): Mistral 0.481 → **RAG 0.875**, FT 0.504, FT(paraphrase) 0.588; Llama2-т FT **буурсан** 0.353 → 0.219.
- Нэг баримтыг олон хэлбэрээр (paraphrase) давтах тусам FT сайжирна (монотон) — «мэдлэгийг олон янзаар давтах хэрэгтэй».
- RAG-ийн сул тал: хэдэн баримт (K) авах нь тогтворгүй.
- **Манайд:** дүрэм журам, KPI тодорхойлолтыг жинд «шингээх» нь RAG-аас муу. Манай хэмжилт ч үүнтэй нийцнэ (RAG +12.0, FT +1.4 пункт).
  Анхаар: энэ нь хяналтгүй FT; манайх асуулт→SQL SFT тул шууд биш, чиглэлээр л баталгаа.

## 2. Gekhman нар, «Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?», EMNLP 2024 (arXiv 2405.05904)
- PaLM 2-S, EntityQuestions (хаалттай QA). Сургалтын жишээг загвар урьд нь мэдэх эсэхээр ангилсан (SliCK): HighlyKnown 24%, MaybeKnown 23%, WeaklyKnown 17%, **Unknown 36%**.
- Unknown (шинэ баримт) жишээ **удаан** сурагдана; сурагдсаны дараа шугаман байдлаар hallucination-ыг ихэсгэнэ (Known-ийн эерэг нөлөөтэй тэнцүү хэмжээний сөрөг нөлөө; R² 0.86 / 0.95).
- Early stopping хамгийн сайн; Unknown-ийг хасвал хэт сургалтын хохирол арилна. Зөвхөн MaybeKnown дээр сургавал хамгийн өндөр (43.6).
- Unknown-ийг «Мэдэхгүй» гэж дахин шошголох → хариулсан асуултын нарийвчлал 43.0 → **61.8** (хариулах хувь 59 → 56%).
- **Манайд:** (а) Arctic-т шинэ баримт (босго, дансны код, хүснэгтийн нэр) заах нь буруу зүйл «итгэлтэй» бичих эрсдэл; (б) загвар аль хэдийн мэддэг SQL/санхүүгийн
  логикийг «ашиглах»-ыг заах нь зөв; (в) **хариулах боломжгүй асуултад татгалзахыг заах** нь нотлогдсон ашигтай арга (манай S4); (г) early stopping, dev-ээр хянах.

## 3. Soni нар, «Schema on the Inside», AAAI 2026 (arXiv 2603.24023, Dream11 CriQ)
- Тохиолдол: крикетийн статистикийн **нэг, өөрчлөгдөхгүй** схем; Gemini Flash + 17k токен prompt (EX 95.6%, утгын зөв 89.4%) → өөрийн Qwen3-8B.
- Өгөгдөл: апп-ын логийн 11k асуулт → QwQ-32B-ээр SQL үүсгэж, гүйцэтгэлээр шүүсэн; нийт **230k** сургалтын жишээ (80k бүтэн-контекст, 15k схем цээжлэх, 150k зөвхөн DB ID-тай). 8×H100, LoRA r64.
- Үр дүн: execution success 98.4%, semantic accuracy 92.5% (LLM шүүгч), prompt 17k → <100 токен.
- Ablation: нэг шаттай (бүтэн контекстгүй) 74.96%; схем цээжлэх алхамгүй 87.2% / 79.5%; 0.6B 93.5/83.7, 1.7B 94.0/87.8, 8B 98.4/92.5.
- Тэдний өөрсдийн хязгаарлалт: «схем статик; ихээхэн өөрчлөгдвөл дахин fine-tune хийх шаардлагатай».
- Анхаар: «execution accuracy» = алдаагүй ажилласан SQL-ийн хувь (зөв эсэх биш); зөв эсэхийг LLM шүүгчээр — манай EX (gold-той харьцуулсан)-тэй шууд харьцуулахгүй.
- **Манайд:** «DB бүтцийг цээжлүүлэх» нь ажилладаг, гэхдээ (а) ~100 дахин их өгөгдөл (манайд 635 жишээ, 500 eval), (б) схем тогтмол байх нөхцөлтэй — Ard Credit-ийн
  view/багана өөрчлөгдөх бүрт дахин сургана, (в) гол ашиг нь хурд/зардал (prompt богино), нарийвчлал +3 орчим. Манай «тогтмол мэдлэг»-ийн зорилгод (схем
  солигдоход ажиллах) **эсрэг чиглэл**.

## 4. EvoSchema (PVLDB 18; arXiv 2603.10697)
- BIRD дээр 10 төрлийн схемийн өөрчлөлт (багана/хүснэгт нэмэх, хасах, нэр солих, хуваах, нэгтгэх); NLQ хэвээр, SQL-ийг шинэчилсэн; eval-ийг хүн шалгасан.
- Ердийн сургалттай Code Llama-7B: EX эх 58 → хүснэгт нэмэхэд 40, хүснэгт хуваахад 38, нэгтгэхэд 43, багана хуваахад 41. Хүснэгтийн түвшний өөрчлөлт хамгийн хортой.
- Ижил асуултыг **олон өөр схемтэй** хослуулж сургавал: багана хуваахад EX +24 хүртэл, хүснэгт нэмэхэд +19, хуваахад +12. Эх схем ба энгийн өөрчлөлтөд **бага зэрэг буурдаг**.
- Хасагдсан хүснэгт/баганад татгалзахыг сургавал эх өгөгдөл дээр хэт татгалзах нэмэгдсэн; out-of-scope-ийн 16%-д SQL бичсэн хэвээр.
- Зөвхөн хамааралгүй хүснэгт нэмэх нь бусад төрөлд хортой — бүрэн холимог хэрэгтэй; хүснэгтийн түвшний хувиргалтыг хасвал тэр төрлөөр ~30 пункт буурна.
- **Манайд:** `t2s_inv`-ийн S2 (нэр сольсон 2 516 жишээ) зөв чиглэл, гэхдээ **зөвхөн нэр солих** нь EvoSchema-д хамгийн бага нөлөөтэй төрөл. Хүснэгт нэмэх/хуваах/нэгтгэх,
  багана хуваах/нэгтгэх хувиргалтыг S2-т нэмэх хэрэгтэй. Эх схем дээр бага зэрэг уналт гарч болзошгүй (T-1 хаалга). Татгалзах сургалтын хэт татгалзалтыг T-6-аар хянана.

## Нэгтгэл — манай ажилд
| Санаа | Нотолгоо | Шийдвэр |
|---|---|---|
| Дүрэм журам, босго, кодыг жинд цээжлүүлэх | 1, 2: RAG илүү; шинэ баримт hallucination нэмнэ | **Хийхгүй** — RAG/glossary-д (одоогийнх) |
| DB схемийг цээжлүүлэх (Schema on the Inside) | 3: ажилладаг ч 230k жишээ, схем тогтмол байх нөхцөл | Одоогоор **хийхгүй**; хурд/зардал асуудал болвол дараа |
| Олон схем дээр «схем уншиж» сургах | 4: схем өөрчлөгдөхөд +12…+24 EX; эх дээр бага уналт | **Хийнэ** (t2s_inv S2) + хүснэгт/баганын бүтцийн хувиргалт нэмэх |
| Prompt-ын тодорхойлолтыг дагах (counterfactual) | 2: байгаа мэдлэгийг ашиглахыг заах | **Хийнэ** (S3, 64 → ~600) |
| Татгалзахыг сургах | 2: «мэдэхгүй» шошго +18.8; 4: хэт татгалзах эрсдэл | **Хийнэ** (S4) + near-miss жишээ, T-6 хяналт |
| Сургалтын горим | 2: early stopping; Unknown хасах | dev-ээр зогсоох, багахан эпох |

Хүлээгдэх нөлөө (таамаг): одоогийн схем дээр 0…+5 пункт (EvoSchema-д эх дээр бага уналт гарсан тул 0 ч байж болно); схем солигдсон үед + том (EvoSchema: +12…+24);
хариулах боломжгүй асуултын recall сайжирна. Батлахын тулд T-1…T-6 хаалгаар хэмжинэ.

## Суурь Arctic-ийг fine-tune хийх жор (2026-10-27, дээрх 4 өгүүлэл + D2/D3-ийн туршлагаас)
1. **Суурь:** цэвэр Arctic-Text2SQL-R1-7B (D2/D3 adapter дээр давхарлахгүй). Arctic нь RL (GRPO)-оор `<think>…</think><answer>` хэлбэрт сургагдсан → тэр хэлбэрийг эвдэхгүй.
2. **Зорилтот гаралт = Arctic өөрөө үүсгэсэн, PG дээр зөв гарсан хариулт** (rejection sampling, n=4–8). Gekhman: загвар «бараг мэддэг» (MaybeKnown) жишээ хамгийн ашигтай,
   «мэдэхгүй» шинэ баримт hallucination нэмнэ → бүх 8 оролдлого буруу асуултыг сургалтад оруулахгүй (эсвэл S4 шиг татгалзлаар шошгоно).
3. **Өгөгдлийн холимог (~3 000 мөр, T4-д багтах):** S2 схем-хувиргалт 1 500 (нэр солих + EvoSchema-ийн хүснэгт нэмэх/хуваах/нэгтгэх, багана хуваах/нэгтгэх);
   S1 өөр домэйн SQL (BIRD/Gretel finance) 700 — ерөнхий чадвар мартахаас сэргийлнэ; S3 тодорхойлолт дагах 400; S4 татгалзах 200 + near-miss 200.
   Асуулт бүрд 1–2 англи paraphrase (Ovadia). dev/test family бүгд хасна (`exclude_families`).
4. **Prompt = inference-тэй яг ижил** (schema linking-тэй богино prompt, 2–3k токен). D2-ийн 344 мөр prompt хэт урт тул хасагдсан алдааг давтахгүй.
5. **Тохиргоо (`t2s_inv1`):** QLoRA NF4, r 32 / α 64, бүх linear давхарга, LR 1e-4, cosine, warmup 3%, loss зөвхөн гаралтад, **1 эпох** + checkpoint бүрийг dev-ийн 60
   асуултын дэд олонлогоор шалгаж хамгийн сайныг сонгох (early stopping; Gekhman).
6. **Хугацаа (2×T4):** D3: ~8 мөр/алхам, 1.66 мин/алхам (5.5k токен prompt). 3 000 мөр × 2.5k токен ≈ 380 алхам × ~0.8 мин ≈ **5–6 цаг**; + sampling ~2 цаг, dev 2.5 цаг, схем-солилт 1 цаг.
7. **Хаалга:** T-1 (одоогийн схем, I3t/M1a-аас муугүй, McNemar), T-2 (схем-солилт ≤ 3 пункт уналт), T-4 (тодорхойлолт ≥ 85%), T-6 (татгалзах recall ≥ 70%, хэт татгалзах ≤ 3%).
   Давбал л вэб/үндсэн pipeline-д оруулна; test-д эцэст нэг удаа.
