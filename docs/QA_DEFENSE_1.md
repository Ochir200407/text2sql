# Багш нараас асууж магадгүй асуулт ба хариулт

Тоонууд 2026-10-29-ний байдлаар, 2026-10-30-ны бүрэн шалгалт, 2026-10-31-ний дахин шалгалт ба V26-ийн эцсийн test-ээр
(Kaggle, 2026-10-31; test-ийг нэг л удаа ашигласан; `docs/RESULTS_V26.md`) шинэчилсэн (dev = хөгжүүлэлтийн 300 асуулт,
test = шинэ 200 асуулт; «хариулах боломжтой» = 224 / 151).

**Хэмжсэн гол тоо (үүнээс хэтрүүлж хэлэхгүй):** урьдчилан зарласан эцсийн систем — таван тохиргооны чуулга M1ens — test дээр
нийт **110/200 (55.0%)**, хариулах боломжтой **90/151 (59.6%)**, хариулах боломжгүй 6/24, хоёрдмол 14/25 (dev дээр 58.7% /
61.2%). Хамгийн сайн ганц тохиргоо M1a: 101/200 (50.5%), хариулах боломжтой 81/151 (53.6%). M1a → M1ens хариулах боломжтой
+10/−1, **p = 0.012** (dev дээр +11/−1, p = 0.006 — давтагдсан). Гол хэмжүүр нь хариулах боломжтой EX: нийт оноо тодруулга,
татгалзлыг зөвд тооцдог тул «үргэлж тодруулна» гэдэг систем ч test-д 49/200 (24.5%) авна. Мэдрэмж: test-ээс мэдээлэл авсан
13 ба жишээний сантай бараг ижил SQL загвартай 6 асуултыг хасвал M1a 66/132 (50.0%) → M1ens 73/132 (55.3%), +8/−1,
**p = 0.039** (41-р асуулт); харин сургасан орчуулагчийн ахиц I3t → M1a 57 → 66, +21/−12, **p = 0.16 — ач холбогдолгүй** (35,
38-р асуулт). M1ensr (чуулга + dev-ийн дүрэм) test дээр 120/200 (60.0%) ч хариулах боломжтой 87/151 (57.6%) — гол тоо биш
(42-р асуулт). 70%-д **хүрээгүй** (23-р асуулт).
FK-bridge, abstain v2, M1cte, хүснэгтийн тайлбар (table hints) бэлэн боловч **GPU дээр хэмжээгүй**.

## Сэдэв ба зорилго
**1. Энэ систем юу хийдэг вэ?**
Ажилтан монголоор асуулт асуухад түүнийг SQL болгож, байгууллагын өгөгдлийн сангаас тоо гаргаж өгнө. SQL мэдэхгүй хүн
шинжээчид хандахгүйгээр мэдээлэл авах боломжтой болно.

**2. Яагаад ББСБ-ийг сонгосон бэ?**
Өгөгдөл нь бүтэцтэй, тайлан, KPI ихтэй, нууцлал чухал. Бодит хэрэгцээ байгаа бөгөөд монгол хэлний шийдэл байхгүй.

**3. Шинэлэг тал юу вэ?**
Монгол хэл дээр Text-to-SQL-ийг анх удаа системтэй хэмжсэн: 500 асуултын үнэлгээний сан, бүрэлдэхүүн бүрийн нөлөөг
статистикаар (McNemar) баталсан, санхүүгийн хэллэгт сургасан орчуулагч, өгөгдлөө гадагш гаргадаггүй нэг GPU-ийн систем.

## Арга
**4. Яагаад шууд монголоор биш, англи хэл рүү орчуулж байна вэ?**
Ижил асуултын англи хувилбарт суурь загвар кирилл хувилбараас 10 дахин олон зөв хариулсан (43 ба 4). Ижил кодоор хэмжихэд
Qwen-ийн (нэмж сургаагүй, zero-shot) орчуулга dev дээр +7.7 хувь нэмсэн (58 → 81, +51/−28, p = 0.013; хариулах боломжтой
+46/−19, p = 0.001; D2 adapter монгол асуултаар сургагдсан тул энэ ахицад prompt-ын зөрүү ч холилдсон — 39-р асуулт). Өмнө хэлж байсан
+11.3 нь boolean алдаа засагдахаас өмнөх кодтой D2-той харьцуулсан тул кодын засварын +3.7-г агуулж байсан. Test дээр
орчуулгыг дангаар нь хэмжээгүй: орчуулга, засвар, татгалзлыг хамт нэмсэн D2 → H4 нийт p = 0.0009 боловч хариулах
боломжтой асуултад +26/−15, p = 0.12 — ахицын ихэнх нь татгалзал, тодруулгаас. Сургасан орчуулагч test-ийн хариулах
боломжтой асуултад p = 0.0066 (test-ээс мэдээлэл авсан 13 асуултыг хасвал p = 0.047; жишээний сантай төстэй 6-г ч хасвал
p = 0.16). Иймд H2 dev дээр батлагдсан, test дээр хэсэгчлэн. Загварууд англи өгөгдлөөр сурсан тул англи асуултыг илүү
ойлгодог.

**5. Яагаад Arctic-Text2SQL-R1-7B вэ?**
Нээлттэй эх, 7B хэмжээтэй тул нэг GPU-д багтана; SQL-д тусгайлан RL-ээр сургагдсан, BIRD дээр 68.5%. Өгөгдөл
байгууллагаас гарахгүй.

**6. RAG гэж юу вэ, яагаад хэрэгтэй вэ?**
Асуулт бүрт мэдлэгийн сангаас хамааралтай хүснэгт, нэр томьёо, DB-ийн утга, жишээ асуултыг хайж prompt-д өгөх арга.
Хамгийн их нэмэр (+12 хувь) өгсөн. DB өөрчлөгдвөл загварыг дахин сургахгүй, мэдлэгийн санг л шинэчилнэ.

**7. Яагаад загвараа өөрөө илүү сургаагүй вэ?**
Сургасан D2-ийн нэмэр бараг алга. Өмнө хэлж байсан B5 → D2-ийн +1.4 хувь холилдсон: B5-ийг Kaggle T4 дээр, D2-ийг Vast
A100 дээр boolean засвараас өмнөх кодоор ажиллуулсан. Ижил код, ижил GPU (A100), орчуулгатай хэмжихэд B5 tr → D2 tr
82 → 81 (+12/−13, p = 1.0). Шалтгаан: өөрийн DB-ийн жишээ prompt хэт урт байснаас сургалтад ороогүй. Өгүүллүүд ч
(Ovadia нар, EMNLP 2024) шинэ мэдлэгийг сургалтаар бус RAG-аар өгөх нь илүү гэж харуулсан. Харин орчуулагчийг сургахад
том нэмэр (+9.8 хувь) гарсан.

**8. MADLAD-ийг хэрхэн сургасан бэ?**
QLoRA (4-bit), 2 828 санхүүгийн асуулт-орчуулгын хосоос үүсгэсэн 8 601 сургалтын мөр (кирилл, латин, холимог г.м.
хувилбар), 2 эпох, Kaggle 2×T4 (DataParallel, бодит batch 64, 270 алхам). Орчуулгын оноо chrF++ 53.5 → 74.8 (сургаагүй
MADLAD → сургасан; Qwen 58.0), нэр томьёо зөв 69.0% (Qwen 46.3%). Сургалтын өгөгдөлд үнэлгээний асуулт ороогүйг шалгасан
(давхцал 0). Гэхдээ өгөгдөл бичих заавар (BRIEF.md) test-ийн орчуулгын алдааг шинжилсний дараа бичигдсэн тул тэндээс
гарсан нэр томьёоны «урхи» (жишээ нь хураагдсан → seized; dev-д 0 удаа) орсон — 35-р асуулт.

**8а. chrF++ гэж юу вэ?**
Машин орчуулгын чанарыг хэмжих оноо (0–100). Загварын орчуулгыг хүний бичсэн зөв орчуулгатай тэмдэгт (үсгийн хэсэг) болон
үгийн түвшинд харьцуулж, давхцлыг тооцно. Үсгийн түвшинд харьцуулдаг тул үгийн хэлбэр бага зэрэг өөр байхад шийтгэл бага.
MADLAD сургалтаар 53.5 → 74.8 болсон нь (Qwen 58.0) орчуулга зөв орчуулгатай илүү ойртсоныг харуулна.

**9. Хариулах боломжгүй асуултад юу хийдэг вэ?**
Хувийн мэдээлэл, өгөгдөл өөрчлөх, DB-д байхгүй мэдээлэл асуувал татгалзана; хоёрдмол бол тодруулна. Буруу тоо хэлэхээс
«мэдэхгүй» гэх нь санхүүд илүү аюулгүй. Гэхдээ энэ хэсэг сул хэвээр: эцсийн M1ens (M1a ч адил) test дээр хариулах
боломжгүй 24-өөс 6, хоёрдмол 25-аас 14-ийг зөв шийдсэн (dev-ээр сонгосон дүрэмтэй E4-д 10 ба 16, үүний 4 нь dev-д гараагүй
түлхүүр үгээс; dev-ийн дүрэмтэй M1ensr-д 14 ба 19, мөн тэр 4 үгтэй — 42-р асуулт; итгэлийн босготой E3c-ийн 17 ба 17 нь
test дээр харж онцолсон, post hoc тоо).

## Үнэлгээ
**10. Нарийвчлалыг яаж хэмжсэн бэ?**
Загварын бичсэн SQL-ийг ажиллуулж, үр дүнг урьдчилан бичсэн зөв SQL-ийн үр дүнтэй харьцуулна (execution accuracy, EX).
Хоёр тохиргооны ялгааг асуулт бүрээр хослуулж McNemar тестээр шалгасан.

**11. Dev ба test яагаад тусдаа вэ?**
Dev дээр системийг тааруулж, test-ийг зөвхөн эцэст нэг удаа хэмжинэ — dev-д хэт тааруулсан эсэхийг шалгахын тулд.
Test-ийн асуултууд dev-ээс өөр «гэр бүл»-ийнх. Гэхдээ гэр бүлээр давхцалгүй ч SQL загвараар бүрэн давхцалгүй биш:
few-shot жишээний санд test-ийн 6 асуулттай бараг ижил SQL загвартай жишээ бий (35-р асуулт).

**12. Gold SQL (зөв хариу) өөрөө зөв гэдгийг яаж мэдэх вэ?**
Бүгдийг DB дээр ажиллуулж шалгасан (хоосон биш үр дүнтэй). Нэмж 178 асуултыг схем, нэр томьёотой тулгаж уншиж шалгасан:
буруу 0, эргэлзээтэй 6. Санамсаргүй 70 асуулт бүгд зөв (алдаа ~4%-иас бага). Нээлттэй асуудал (G1): 13 gold SQL (dev 9,
test 4) USD ба MNT дүнг ханшаар хөрвүүлэлгүй нэмж байж болзошгүй; PostgreSQL дээр `currency_code`-ийн тархалтаар хараахан
шалгаагүй. Иймд «буруу 0» нь энэ асуудлыг шалгаагүй үеийн дүн.

**13. 55.0% бага биш үү?**
Test дээрх эцсийн дүн 55.0% (урьдчилан зарласан чуулга M1ens; хариулах боломжтой 59.6%); хамгийн сайн ганц тохиргоо M1a
50.5% (53.6%). E3c-ийн 46.5% нь 8 хувилбартай салаанд test дээр хамгийн өндөр байсан ч dev-ээр сонгогдоогүй (dev-д E4 159 >
E3c 137) тул post hoc — тэр салааны dev-ээр сонгосон тохиргоо E4 нь 45.0% (dev-д дэмжлэгтэй түлхүүр үгээр нийт 43.0%;
хариулах боломжтой 42.4% хэвээр). Монгол хэл, 7B загвар, нэг GPU гэсэн нөхцөлд нэмэлт сургалттай суурь D2-ийн 21.0%-иас 2.6
дахин өссөн (хариулах боломжтой 24.5% → 59.6%). Англи BIRD дээр том системүүд 70% орчим боловч тэдгээр нь англи хэл, олон DB,
татгалзалтгүй үнэлгээ тул шууд харьцуулахгүй. Алдааны 38% нь орчуулгаас (E2, dev) байсан тул орчуулагчийг сургасан —
test-ийн хариулах боломжтой асуултад 41.1% → 53.6% (+32/−13, p = 0.0066; test-ээс мэдээлэл авсан 13 асуултыг хасвал
p = 0.047, загвар төстэй 6-г ч хасвал p = 0.16), dev дээр 56.7% (+40/−18, p = 0.0054). Үүн дээр таван тохиргооны чуулга
хариулах боломжтой асуултад 6.0 хувь нэмсэн (53.6% → 59.6%, +10/−1, p = 0.012).

**14. Өгөгдөл бодит уу?**
Үгүй — бодит харилцагчийн мэдээлэл ашиглаагүй, ББСБ-ийн бүтэцтэй синтетик өгөгдөл (seed 42, давтагддаг). Энэ бол
хязгаарлалт; дараагийн алхам — хамгаалалттай бодит хуулбар дээр турших.

## Хязгаарлалт ба цаашид
**15. Гол сул тал юу вэ?**
(1) Синтетик, ганц өгөгдлийн сан; (2) үнэлгээний санг хүн шинжээч шалгаагүй; (3) хурд: нэг үүсгэлттэй тохиргоо T4 дээр
асуулт бүрт ~20–30 с, 8 хувилбартай үед медиан ~72 с, p95 ~6 мин; эцсийн чуулга таван тохиргоог ажиллуулдаг тул тооцоолол
~5 дахин (T4 дээр гишүүн бүр ~26–34 с/асуулт); (4) орчуулагч DB-ийн код, шошгыг хадгалах нь сул (13.6%);
(5) хариулах боломжгүй асуултыг таних сул (test 6/24); (6) test 200 асуулт тул ±7 хувийн итгэх завсар; (7) үнэлгээний
хүчинтэй байдлын эрсдэл (E4-ийн 2 түлхүүр үг, MT-ийн заавар, жишээний сангийн SQL загвар) — 35-р асуулт.

**16. Хурдыг яаж сайжруулах вэ?**
Илүү хүчтэй GPU (A100/L4), 8 хувилбарын оронд итгэл өндөр үед 1 хувилбар, prompt-ийг богиносгох (schema linking).

**17. Цаашид юу хийх вэ?**
Сургасан орчуулагчийн ахиц test дээр ач холбогдолтой (p = 0.0066), гэхдээ test-ээс мэдээлэл авсан 13 асуултыг хасахад
p = 0.047 болж суларна, жишээний сантай төстэй 6-г ч хасвал p = 0.16 (38-р асуулт). Dev дээр батлагдсан чуулгыг (M1ens) test
дээр нэг удаа хэмжиж батлав: 55.0%, хариулах боломжтой 59.6%, M1a-аас +10/−1, p = 0.012 (41-р асуулт). Дараагийн алхам: олон
хувилбараас зөвийг сонгогчийг сайжруулах (test дээр таван гишүүний аль нэг нь зөв хариулсан асуулт 102/151 = 67.5%, чуулга
90-ийг нь сонгосон; dev дээр 155/224 = 69.2%); бэлэн боловч хэмжээгүй сайжруулалтуудыг (abstain v2, M1cte, FK-bridge) dev
дээр шалгах; test ашиглагдсан тул шинэ, хөндөгдөөгүй асуулт дээр дахин баталгаажуулах; бодит орчинд турших.
Сургасан reranker нэр томьёоны хамралтыг 77% → 79% болгосон ч SQL-д ялгаа батлагдаагүй (p = 0.60) — дахин сургахаас
илүү сонголт руу анхаарна. Дэлгэрэнгүйг 34-р асуултаас үз.

**18. Өөр байгууллагад ашиглаж болох уу?**
Тийм — мэдлэгийн санг (схем, нэр томьёо, жишээ) шинэ DB-д тааруулахад хангалттай, загварыг дахин сургах шаардлагагүй.
Гэхдээ энэ нь зөвхөн нэг синтетик DB дээр хэмжигдсэн тул өөр DB дээр нарийвчлал ижил байна гэж баталж чадахгүй.

## Нэмэлт асуултууд (2026-10-29): статистик, SQL-ийн чанар, 70%, шинэ ажлууд

**19. Test 200 асуулт хангалттай юу? Итгэх завсар хэд вэ?**
Wilson-ы 95% итгэх завсар: эцсийн M1ens нийт 110/200 (55.0%) → 48.1–61.7% (±7 хувь орчим), хариулах боломжтой 90/151
(59.6%) → 51.6–67.1% (±8 хувь); M1a 101/200 → 43.6–57.4%, 81/151 → 45.7–61.4%. Тиймээс хоёр тохиргооны хэдэн хувийн ялгааг
завсраар нь харьцуулж дүгнэх боломжгүй. Үүний оронд ижил асуултууд дээр хослуулсан McNemar тест хэрэглэсэн: энэ нь зөвхөн
«нэг нь зөв, нөгөө нь буруу» асуултуудыг тоолдог тул илүү мэдрэмтгий. Жишээ нь M1a ба M1ens-ийн завсар давхацдаг ч ижил
асуултаар хослуулахад +10/−1, p = 0.012 — ялгаа санамсаргүй биш; сургасан орчуулагч test дээр 41.1% → 53.6% (+32/−13,
p = 0.0066; 13 асуултгүйгээр p = 0.047; загвар төстэй 6-г ч хасвал 0.16). BIRD dev (1 534 асуулт)-тэй
харьцуулахад манай test жижиг — үүнийг хязгаарлалт гэж тайланд бичсэн. (Өмнө тайланд bootstrap завсар байсныг Wilson
болгож нэгтгэв.)

**20. Яагаад синтетик өгөгдлийн сан ашигласан бэ, энэ нь дүгнэлтийг хэрхэн хязгаарлах вэ?**
Бодит ББСБ-ийн харилцагчийн мэдээллийг дипломын ажилд ашиглах зөвшөөрөл, нууцлалын баталгаа байхгүй. Иймээс ББСБ-ийн бүтэцтэй
28 хүснэгт, 425 багана, ~650 мянган мөртэй синтетик DB-г (seed 42, давтагддаг) үүсгэсэн; мөн 8 өөрчилсөн хуулбар DB-ээр
(test-suite) санамсаргүй таарахаас сэргийлсэн. Хязгаарлалт: бодит өгөгдөл илүү бохир (NULL, хуучин код, давхардал), бодит
хэрэглэгчийн хэллэг өөр, асуулт ба gold SQL-ийг LLM agent бичиж өөр agent хянасан. Тиймээс дүгнэлт «энэ схем ба асуултын
тархалт дээр» л хүчинтэй; бодит орчинд ижил тоо гарна гэж мэдэгдэхгүй.

**21. EX-ээс гадна SQL-ийн чанарыг яаж үнэлсэн бэ?**
Буруу SQL gold-оос хэр хол байгааг sqlglot-оор бүтцээр нь харьцуулсан: хүснэгтийн precision/recall, баганын ба WHERE-ийн
баганын хамралт, агрегат таарсан эсэх, илүү JOIN, AST-ийн хэмжээ, «ойр алдаа» (soft-F1 ≥ 0.5). Dev дээр хүснэгтийн recall
93–94%, агрегат 81–83% таарч байхад хариулах боломжтой асуултын EX 37–48% байсан — бүтэц ойролцоо, алдаа нарийн хэсэгт гарч
байна. Хэмжээний харьцаа ≈1.0–1.1 тул загвар SQL-ийг хэт төвөгтэй болгодоггүй. Шударга тэмдэглэл: энэ шинжилгээ C1–E5h_w3
run-ууд дээр хийгдсэн; эцсийн M1-ийн асуулт бүрийн бүтэн гаралт Kaggle-д байгаа тул M1-ийн бүтцийн шинжилгээг хийгээгүй.

**22. Буруу хариултын гол шалтгаан юу вэ?**
Алдаа бүрт нэг шалтгааныг эрэмбээр оноосон (хариулах боломжтой асуулт): шүүлтийн багана дутуу 26–31%, агрегат/GROUP BY
21–26%, хүснэгт буруу/дутуу 13–27%, бүтэц ижил ч утга/нөхцөл буруу 10–25%. Анхны хувилбарт CTE-ийн түр нэрийг хүснэгт гэж
тоолсон тул хүснэгтийн алдаа 28–40% гэж хэт өндөр гарсан байсан; үүнийг засаад дахин тооцсон. Хүснэгтийн алдааны ихэнх нь
хайлтаас биш, загвар төстэй хүснэгтийг андуурснаас (loans ↔ loan_applications, deposits ↔ accounts) үүдэлтэй. Өмнөх E2-ийн
гар ангиллаар алдааны 38% нь орчуулгаас байсан бөгөөд үүнийг сургасан орчуулагчаар багасгасан.

**23. Яагаад 70%-д хүрээгүй вэ? Хүрэх боломжтой юу?**
Test дээр 70% гэдэг нь 140/200; эцсийн M1ens 110, дутуу нь 30 асуулт. V26-аас өмнө чуулга + дүрэм + хос харьцуулалтаар
≈117–123 (59–62%) гэж таамаглаж байсан; хэмжихэд урьдчилан зарласан M1ens 110 (55.0%), dev-ийн дүрэмтэй M1ensr 120 (60.0%;
гол тоо биш — 42-р асуулт), хос харьцуулалтыг (pick) test дээр ажиллуулаагүй. Хязгаар ч бий: test дээр таван гишүүний аль нэг
нь зөв хариулсан хариулах боломжтой асуулт 102/151 (67.5%; dev дээр 155/224 = 69.2%) тул зөвхөн сонголтоор үүнээс давахгүй.
Сул хэсгүүд нь хүнд (M1ens test 11/31), домэйн хоорондын (5/18; M1a 2/18), хариулах боломжгүй (6/24) асуулт бөгөөд эдгээрт
шинэ төрлийн генератор, татгалзалтын ангилагч хэрэгтэй. 70%-ийг «хүрнэ» гэж хэлэхгүй; test-ийг нэг л удаа хэмжсэн — түүгээр
дахин тааруулахгүй.

**24. Dev дээр 65.7% байхад яагаад гол тоо 55.0% вэ?**
Dev-ийн M1ensr 197/300 (65.7%)-д dev-ийн хэллэгээс бичсэн татгалзал/тодруулгын дүрэм орсон тул энэ нь in-sample, өөдрөг тоо;
test дээр 120/200 (60.0%), хариулах боломжтой нь 87/151 (57.6%) болсон (42-р асуулт). Гол тоо нь V26-аас өмнө урьдчилан
зарласан чуулга M1ens: dev дээр хариулах боломжтой 137/224 (61.2%; нийт 176/300 = 58.7%; M1a-аас +11/−1, p = 0.006), test
дээр нэг удаа хэмжихэд 90/151 (59.6%; нийт 110/200 = 55.0%; M1a-аас +10/−1, p = 0.012). Dev → test хариулах боломжтой
асуултад ердөө 1.6 хувь буурсан нь чуулгын dev-д хэт тааруулалт бага байгааг харуулна.

**25. Abstain v2 юу харуулсан бэ?**
Abstain v2 нь гар дүрмийн оронд 15 ерөнхий шинж (хувийн мэдээлэл, бичих үйлдэл, ирээдүйн огноо, мэдлэгийн санд байхгүй үг,
хоёрдмол нэр томьёо г.м.) дээр логистик регресс сургасан ангилагч. Dev дээр family-аар 5-fold × 10 давталтаар: v2 154.5 ± 1.7,
dev-ээс бичсэн дүрэм 159 (in-sample), дүрэм + v2 160.9 ± 1.0. Өөрөөр хэлбэл v2 дүрмийг **давсангүй**: хариулах боломжгүй ба
хоёрдмолд ойролцоо, гэхдээ хариулах боломжтой ~5 асуултыг буруу татгалзаж/тодруулж алдсан. Итгэлийн шинж (санал нийлэлт г.м.)
CV-д нэмэр өгөөгүй. GPU-гүй, офлайн тооцоо; онлайн дамжлагад холбоогүй.

**26. Abstain v2 дүрмийг давсангүй бол яагаад хэрэгтэй вэ?**
Нэгдүгээрт, дүрмийн 159 нь dev-ийг харж бичсэн тул out-of-sample биш; v2-ийн 154.5 нь dev-ийн өөр «гэр бүл» дээр шалгасан
шударга тооцоо — test дээр дүрэм ба v2-ийн зөрүү багасах төлөвтэй. Хоёрдугаарт, v2 нь шинэ DB-д дүрэм дахин бичихгүйгээр
шилжих ерөнхий шинж ашигладаг. Гуравдугаарт, хоёрыг хослуулахад CV 160.9 болж хамгийн өндөр гарсан. Мөн «итгэлийн шинж
тусалдаггүй» гэсэн сөрөг үр дүн нь өөрөө мэдээлэл. Шинжийн бүлгийг dev-ийг уншсаны дараа бичсэн тул CV ч бага зэрэг өөдрөг;
test дээр хэмжээгүй тул ахиц гэж мэдэгдэхгүй.

**27. FK-bridge гэж юу вэ, яагаад их ахиц өгөхгүй гэж үзэж байна вэ?**
FK-bridge нь хайлтаар олдсон хүснэгтүүдийн хооронд FK-ээр холбох завсрын хүснэгтийг (≤2 нэмэлт) prompt-д нэмдэг. Dev дээр
офлайн шалгахад gold хүснэгт бүгд prompt-д орсон хувь 97.3% → 99.1% болсон. Гэвч gold хүснэгт аль хэдийн 97% тохиолдолд
prompt-д байгаа, M1a-д 28 хүснэгтийн DDL бүгд ордог, хүснэгтийн алдаа голдуу загвар төстэй хүснэгтийг андуурснаас үүдэлтэй.
Тиймээс EX-д нөлөө бага гэж таамаглаж байна; GPU дээр хэмжээгүй. Энэ нь RSL-SQL-ийн дүгнэлттэй нийцтэй: recall их өссөн ч EX
ердөө +1.2.

**28. CHASE-SQL, XiYan-SQL, RSL-SQL-тэй харьцуулбал?**
CHASE-SQL олон генератор + сургасан хос сонгогчоор BIRD dev 73.0% (self-consistency 68.8) авсан боловч Gemini ба асуулт бүрт
олон дуудлага шаарддаг. XiYan-SQL-д Qwen2.5-Coder-7B дээр сургасан сонгогч олонхын саналаас +3.1 хувь, харин сургаагүй 7B
сонгогч илүү муу (62.8 ба 69.6) — манай сургаагүй Arctic-ийн A/B сонголт (pick) бага нэмэр өгч магадгүйг анхааруулж байна.
RSL-SQL хоёр чиглэлтэй schema linking-ээр recall-ийг 94% хүргэсэн ч EX-д +1.2 л. Эдгээр нь англи, BIRD, том/хаалттай загвар
дээр хэмжигдсэн тул тоог шууд харьцуулахгүй; манай ажил тэдний санааг монгол хэл, нэг GPU, татгалзалттай нөхцөлд шилжүүлсэн.

**29. Шинэлэг тал ба судалгааны цоорхой юу вэ?**
Бидний хайлтаар (2026-10) монгол хэлний Text2SQL-ийн нийтэд нээлттэй сан, систем олдсонгүй. 2025–2026-ийн ажлууд (XiYan,
JudgeSQL, RSL-SQL, SQL-R1) англи хэл дээр, бага нөөцтэй хэлнийх (BIRDTurk, BIRD_PT, MultiSpider 2.0) сан эсвэл үнэлгээ санал
болгосон, систем биш. Манай ажил: (1) 3 бичигтэй, хариулах боломжгүй ба хоёрдмол асуулттай 500 асуултын сан; (2) орчуулга,
RAG, сургалт, санал хураалт, чуулгын нөлөөг нэг DB дээр McNemar-аар тус тусад нь хэмжсэн; (3) нэг GPU-д чиглэсэн нээлттэй
систем. «State of the art» гэж хэлэхгүй — харьцуулах монгол систем байхгүй.

**30. Нууцлал ба нэг GPU дээр байршуулах талаар?**
Бүх загвар нээлттэй (Arctic-Text2SQL-R1-7B, MADLAD-400-3B, BGE-M3) тул байгууллагын дотор ажиллаж, өгөгдөл гадны API руу
гарахгүй. Үнэлгээг Kaggle T4 (16 GB) ба Vast A100 дээр хийсэн: C, D2, H, E1 ба dev-ийн E2 (мөн test-ийн D2, H4) — A100;
A, B, I, M бүлэг ба test-ийн E2 — T4. D2-ийг Vast A100, D3 ба MADLAD-ийг Kaggle T4×2 дээр сургасан (C-г Modal A100 дээр);
хугацааг T4×2 дээр хэмжсэн. Хамгаалалт давхаргатай:
хувийн мэдээллийн асуултыг дүрмээр татгалзах, хувийн баганагүй view, унших эрхтэй read-only холболт, шифрлэгдсэн аудит.
Хязгаарлалт: 8 хувилбартай үед хариулт удаан (p95 ~6 мин), бодит орчинд илүү хүчтэй GPU эсвэл нэг үүсгэлттэй горим хэрэгтэй.

**31. Studio-д юу нэмсэн бэ, аюулгүй юу?**
Долоон боломж: SQL-ийн монгол тайлбар, итгэлийн түвшин (хувилбаруудын санал нийлэлт — зөв байх магадлал биш), мөрийн
хязгаар/timeout-ийн мэдэгдэл, автомат график, CSV/Excel татах, асуултын түүх, 👍/👎 үнэлгээ. Бүгд нэмэлт LLM дуудахгүй, DB-д
дахин хандахгүй. SQL guard, read-only транзакц, statement_timeout (20 с), EXPLAIN өртгийн хязгаар, 1000 мөрийн LIMIT
өөрчлөгдөөгүй; шинэ endpoint-ууд үйлчлүүлэгчээс SQL хүлээж авдаггүй. Excel/CSV-д `=`, `+`, `-`, `@`-ээр эхэлсэн нүдэнд `'`
нэмж томьёо шахалтаас хамгаална. 👍 авсан жишээ «хянах» төлөвт ордог, мэдлэгийн санд автоматаар бичигдэхгүй; 25 unit тесттэй.

**32. Dev ба test хооронд мэдээлэл алдагдахаас (leakage) яаж сэргийлсэн бэ?**
Асуултыг загварын «гэр бүл»-ээр dev/test-д хуваасан (давхцал 0). MADLAD-ийн сургалтын 8 601 мөр (2 828 хос), reranker-ийн шошго,
мэдлэгийн сангийн жишээ нь үнэлгээний асуултын текстээс тусдаа гэж шалгасан. Дүрэм, босго, чуулгын бүрэлдэхүүнийг зөвхөн dev
дээр сонгож, test дээр dev-тэй яг ижил бүрэлдэхүүнээр ажиллуулсан (V26: суурь M1rr + M1ks, M1a, M1g8, M1m; гол тоо M1ens-ийг
урьдчилан зарласан); хос харьцуулалтыг (pick) зөвхөн dev дээр ахисны дараа test-д хэрэглэх дүрэмтэй байсан тул test дээр
ажиллуулаагүй. Шударга тэмдэглэл: dev-ээс бичсэн дүрэм dev-ийн тоог өөдрөг болгодог тул test-ийн тоог гол гэж үздэг; мөн test
дээр хэд хэдэн тохиргоог тайлагнасан нь олон харьцуулалтын эрсдэлтэй. 2026-10-30-ны шалгалтаар гурван сул тал илэрсэн:
(1) E4-ийн «таамаг», «өрсөлдөгч» түлхүүр үг dev-ээс биш, үнэлгээний сан үүсгэх заавраас (AUTHORING.md) орсон, зөвхөн
test-ийн 4 асуултад ажилласан; (2) MT өгөгдөл бичих заавар test-ийн орчуулгын алдааны шинжилгээний дараа бичигдсэн
(13 асуулт); (3) few-shot санд test-ийн 6 асуулттай бараг ижил SQL загвартай жишээ бий. Тохируулсан тоог 35-р асуултад үз.
V26-д (1) нь M1ensr-ийн дүрэмд давтагдсан тул M1ensr гол тоо биш (42-р асуулт); гол M1ens дүрэмгүй.

**33. Яагаад нэр томьёоны reranker, M1g8, M1ks-ийг ахиц гэж тооцоогүй вэ?**
Dev дээр M1a-тай харьцуулахад ялгаа нь статистикийн хувьд батлагдаагүй: M1rr +18/−14 (p = 0.60), M1g8 +13/−14 (p = 1.0),
M1ks +15/−12 (p = 0.70). Test дээр ч (V26) аль нь ч M1a-аас ялгаагүй: M1ks 50.0% (хариулах 54.3%; +7/−6), M1rr 50.0%
(53.6%; +15/−15), M1g8 48.0% (49.0%; +5/−12, p = 0.14), M1m 51.0% (54.3%; +1/−0). Reranker нэр томьёоны хамралтыг
сайжруулсан ч загвар тэр мэдлэгийг SQL-д ашиглахгүй байгаа бололтой. Харин эдгээр тохиргоо өөр өөр асуултыг зөв хариулдаг
тул чуулгад нэгтгэхэд ахиц батлагдсан (M1ens: dev p = 0.006, test p = 0.012). Сөрөг үр дүнг нуулгүй тайлагнасан.

**34. Цаашид юу хийх вэ (тодорхой дараалал)?**
Хийгдсэн: dev-ээр сонгосон чуулгыг test дээр нэг удаа хэмжсэн (V26; M1ens 55.0%, хариулах 59.6%, p = 0.012 — 41-р асуулт).
Цаашид: (1) Сургасан хос сонгогч (CHASE/XiYan маягаар, синтетик асуулт дээр) — test дээр таван гишүүний нэгдэл 67.5% байхад
чуулга 59.6%. (2) Бэлэн боловч хэмжээгүй сайжруулалтыг dev дээр шалгах: CTE/дэд алхмын генератор (M1cte), abstain v2,
андуурагддаг хүснэгтийн тайлбар (table hints), FK-bridge. (3) Өөрийн схемд зориулсан синтетик өгөгдлөөр дахин сургах.
(4) Test ашиглагдсан тул шинэ, хөндөгдөөгүй асуултын сан бэлтгэж дахин баталгаажуулах. (5) Бодит, хамгаалалттай өгөгдөл ба
бодит хэрэглэгчийн асуулт дээр турших; хариултын хугацааг (чуулга — 5 тохиргоо) багасгах.
