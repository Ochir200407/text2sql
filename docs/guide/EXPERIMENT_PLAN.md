# Туршилтын төлөвлөгөө: Arctic-Text2SQL-R1-7B ба sqrl-9b
Хоёр загварыг ижил монгол eval set, ижил DB snapshot дээр дөрвөн бүлгээр туршина: суурь загварыг шууд, суурь загварыг RAG ба few-shot-тэй, зөвхөн fine-tune хийсэн загварыг, fine-tune хийсэн загварыг RAG ба few-shot-тэй. Бүлэг бүрт нэг удаад нэг өөрчлөлт хийж нөлөөг нь хэмжинэ. Шилдэг тохиргоо одоогийн системийг ижил тест дээр давсан үед л түүнийг солино.
## Судалгааны асуултууд
Туршилтын бүлэг бүр доорх асуултуудын нэгд хариулна.
1. A. Шууд ашиглахад хоёр загвар монгол асуултад ямар нарийвчлалтай вэ? Англи, галиг асуултаас хэр зөрүүтэй вэ, англи руу орчуулах нь тусалдаг уу, DB SQLite биш бол dialect-ийг яаж шийдэх вэ?
2. B. RAG-ийн бүрэлдэхүүн (тайлбар, утгын хайлт, нэр томьёо) ба few-shot тус бүр суурь загварт хэдэн оноо нэмдэг вэ?
3. C. Зөвхөн fine-tune хийхэд хэр сайжрах вэ? Англи чадвар буурах уу, ямар өгөгдлийн холимог хамгийн сайн вэ, GRPO нэмэлт ахиц өгөх үү?
4. D. Fine-tune хийсэн загварт RAG ба few-shot нэмэлт ашиг өгөх үү, RAG-тай prompt-оор сургах шаардлагатай юу?
5. A–D. Fine-tune ба RAG-ийн ашиг хоорондоо нэмэгддэг үү, давхардаг уу?
6. E. Алдаагаар засах ба санал хураалт эцсийн тохиргоонд хэр нэмдэг вэ, хугацаа, зардал нь хэд вэ?
7. Шилдэг тохиргоо одоогийн системийг давж, түүнийг солих шалгуурыг хангах уу?
## Хоёр загварын онцлог
Хоёр загвар хоёулаа зөвхөн англи өгөгдөл, SQLite дээр сургагдсан бөгөөд өөр өөрийн prompt протоколтой. Туршилт бүрт загвар бүрийг яг өөрийн протоколоор ажиллуулж, RAG-ийн агуулгыг тухайн протоколын схем, evidence хэсэгт оруулна.

## Туршилтын 4 бүлэг ба үр дүнгийн хүснэгт
Туршилтыг загвар (суурь эсвэл fine-tune) ба context (шууд эсвэл RAG ба few-shot) гэсэн хоёр хүчин зүйлээр дөрвөн бүлэгт хуваана. Гол харьцуулалтад decoding ижил: greedy, нэг удаа, засах давталтгүй. Хүснэгтийн EX нь кирилл dev set-ийн гүйцэтгэлийн нарийвчлал (%); галиг, англи, хугацаа, token-ийг run бүрийн log-д хадгална.
[EMBED caption=2×2 туршилтын загвар · 4 бүлэг, 4 харьцуулалт ref=node/4a7e849f-de0c]
Сум бүр нэг хүчин зүйлийн нөлөөг хэмжинэ. Хоёр «RAG-ийн нөлөө»-г харьцуулбал fine-tune ба RAG-ийн ашиг нэмэгддэг үү, давхардаг уу гэдэг харагдана.
### Бүлгүүд
1. A. Суурь загвар, шууд. RAG, few-shot-гүй, тайлбаргүй түүхий схемтэй. Хэлний зөрүү, орчуулга, dialect-ийг энд шийднэ. Шууд эхлүүлж болно.
2. B. Суурь загвар + RAG, few-shot. Бүрэлдэхүүнийг A1 дээр нэг нэгээр нэмж, дараа нь бүгдээс нэг нэгийг хасна. Шууд эхлүүлж болно.
3. C. Зөвхөн fine-tune хийсэн загвар. A1-ийн prompt-оор (RAG-гүй) сургаж, RAG-гүй үнэлнэ. Сургалтын өгөгдөл бэлэн болсны дараа.
4. D. Fine-tune хийсэн загвар + RAG, few-shot. C-ийн загварт RAG нэмэх (D1) ба RAG-тай prompt-оор сургах (D2)-ыг харьцуулна. C-ийн дараа.
5. E. Inference техник. Алдаагаар засах, санал хураалт, татгалзах босгыг дөрвөн бүлгийн шилдэг тохиргоон дээр л нэмж, production-ий тохиргоог сонгоно.
### Гол харьцуулалт
- RAG ба few-shot-ийн нөлөө, суурь загварт: B5 − A1.
- Fine-tune-ийн нөлөө, RAG-гүй: C-ийн шилдэг − A1.
- RAG ба few-shot-ийн нөлөө, fine-tune хийсэн загварт: D-ийн шилдэг − C-ийн шилдэг.
- Fine-tune-ийн нөлөө, RAG-тай: D-ийн шилдэг − B5.
- Сургалтын prompt-д RAG хэрэгтэй эсэх: D2 − D1. Arctic-32B эхлэх checkpoint-ийнхоо prompt форматыг хэрэглэхэд 67.9-өөс 70.5 болсон; DAIL-SQL-д fine-tune хийсний дараа жишээний ашиг буурсан.

## Шинэлэг санаа ба шинэ аргууд
Шинэлэг хувь нэмэр гаргах хамгийн бодит боломж бол миний хайлтаар судлагдаагүй гурван цоорхой: монгол text2sql benchmark, кирилл ба латин бичгийн хоорондох утга тааруулалт, бичгээс үл хамаарах RL сургалт. Эдгээрийг хослуулбал нэг нийтлэл болохуйц ажил гарна.
### Санаанууд
1. Монгол text2sql benchmark. Шинэ нь: монгол text2sql dataset, судалгаа олдсонгүй.Арга: BIRD-ийн асуултыг BIRDTurk-ийн аргаар монгол руу орчуулж, кирилл ба латин галиг хосоор, хүнээр шалгасан хувилбар гаргана. Компанийн өгөгдлийг оруулахгүй; BIRD нь CC BY-SA 4.0 тул үүсмэл dataset-ийг ижил лицензээр нийтэлнэ.Туршилт: F1.
2. Бичиг хоорондын утга тааруулалт. Шинэ нь: CodeS, CHESS, SEED бүгд нэг бичгийн дотор тааруулдаг. Галиг асуултыг кирилл утгатай холбосон text2sql ажил олдсонгүй; IndicDB-ийн Hinglish нь англи үг агуулдаг тул өөр асуудал.Арга: эхлээд дагавар хасах (Улаанбаатарт → Улаанбаатар) ба дүрмийн галиг хувиргалт. Дараа нь query log-ийн хосоор (галиг оролт → хэрэглэгчийн зөвшөөрсөн кирилл утга) сургасан жижиг хувиргагч.Туршилт: F2, F3.
3. Бичгээс үл хамаарах GRPO reward. Шинэ нь: Kattamuri нар-ын contrastive reward асуултын embedding-ийн төстэй байдлыг шагнадаг. Нэг асуултын кирилл, галиг, англи хувилбарын SQL ижил үр дүн өгөхийг шагнасан ажил олдсонгүй.Арга: асуулт бүрийг гурван хувилбараар rollout хийж, execution reward дээр «бүх хувилбар ижил үр дүн өгвөл» нэмэлт оноо өгнө.Туршилт: F4.
4. Англи pivot reasoning. Шинэ нь: XRICL (2022) англи жишээ хайж ашигласан, Etxaniz нар өөрөө орчуулах нь 0.3–3.5 оноо нэмснийг харуулсан. RL-ээр сургасан text2sql загварт монгол асуултыг reasoning дотор англиар дахин томьёолохыг сургасан ажил олдсонгүй.Эрсдэл: PROPOR 2026-д чөлөөт дотоод reasoning португал хэлэнд 3 оноо бууруулсан тул нэг өгүүлбэрийн дахин томьёоллоор хязгаарла.Туршилт: F5, F6.
5. Ойлголт ба үүсгэлтийг хуваасан хоёр загвартай pipeline. Арга: монгол хэлэнд хүчтэй жижиг загвар (Gemma 4 E4B, Qwen3.5-4B-аас монгол eval дээр сайныг нь) асуултыг англи бүтэцтэй intent JSON болгоно: хүснэгт, метрик, хугацаа, утгыг кириллээр нь. SQL загвар үүнээс SQL бичнэ.Яагаад: NLP2025-д монгол математикт Gemma-2-9B 46.4, Qwen2.5-7B 12.4 авсан; монгол чадвар загвараас ихээхэн хамаардаг бол SQL загварууд англиар сургагдсан.Туршилт: F7, энгийн орчуулгатай (A4) харьцуулна.
6. Монгол semantic layer ба чиглүүлэгч. Арга: зээлийн багц, хугацаа хэтэрсэн зээл зэрэг гол KPI-г semantic YAML-д монгол синонимтой нэг удаа тодорхойлно. LLM асуултыг метрик, хэмжээс, шүүлтүүрийн JSON болгоход compiler SQL-ийг тогтмол дүрмээр үүсгэнэ; бусад асуулт чөлөөт SQL үүсгэлт рүү очно.Нотолгоо: Snowflake Cortex Analyst semantic model-оор дотоод BI асуултад 90%-иас дээш авсан бол ганц prompt-той GPT-4o 51%.Туршилт: F8.
7. Санал зөрөлтөөр сонгох идэвхтэй сургалт. Арга: 8 хувилбар санал зөрсөн production асуултыг л шинжээчдээр тэмдэглүүлж, сургалт ба жишээний санд нэмнэ.Нотолгоо: sqrl-9b-д 8 хувилбар бүгд ижил үед ~87% зөв, зөрсөн үед 19–43% зөв.Туршилт: F9.
8. Монгол утга хайх tool-тэй agent. Арга: sqrl-ийн протоколд 2-р санааны normalizer дээр ажилладаг search_values tool нэмнэ.Өмнөх ажил: ReToolSQL BM25 ба regex утга хайх tool-тойгоор BIRD-test-д 78.14% авсан.Туршилт: F10, протокол өөрчлөгдөх тул D бүлгийн сургалт шаардана.
### Санал болгох дараалал
- Эхлээд 2 ба 6: хямд бөгөөд бизнест шууд үр өгөөжтэй. 1-ийг eval-д хэрэгтэй тул зэрэг эхлүүл.
- Дараа нь 3, 5, 4; хамгийн сүүлд 7, 8.
- Нийтлэлийн сэдэв: 1, 2, 3-ыг нэгтгэвэл «бичгээс үл хамаарах монгол text2sql: benchmark, бичиг хоорондын утга тааруулалт, тогтвортой RL» гэсэн ажил болно.
- Хийхгүй байх: монгол хэлээр нэмэлт pretrain, tokenizer өргөтгөл. Зардал өндөр, монгол instruction tune reasoning-ийг эвдсэн (NLP2025), TriMix монгол хэлэнд бага ахиц өгсөн.

## Туршилтын дүрэм
Үр дүнг итгэж болохуйц болгох гол нөхцөл бол нэг удаад нэг өөрчлөлт, бүх зүйлийг хувилбарлах, шийдвэрийг ач холбогдлын тестээр гаргах.
- Нэг удаад нэг өөрчлөлт. Run бүр эх тохиргооноосоо зөвхөн нэг зүйлээр ялгаатай байна (Databricks Genie-гийн зарчим).
- Бүгдийг хувилбарла. Eval set (v1), DB snapshot-ийн огноо, prompt template, загварын revision (Hugging Face commit), кодын commit-ийг run бүрт бич.
- Dev ба test-ийг тусгаарла. 500 асуултыг 300 dev, 200 test болгон хуваа. Шийдвэрийг dev дээр гаргаж, test-ийг бүлэг бүрийн төгсгөлд л ажиллуул. Нэг загварын (template) асуултууд нэг талдаа байна.
- Сургалтын өгөгдлийг цэвэрлэ. Dev, test асуулт болон тэдгээрийн өөрчилсөн хувилбар сургалтад орохгүй; embedding-ийн төстэй байдлаар давхардлыг шүү.
- Давталт. Greedy run-ийг нэг удаа, sampling-тэй run-ийг 3 seed-ээр ажиллуулж дундаж ± стандарт хазайлтыг бич.
- Асуулт бүрийн log. JSONL-д question_id, config_id, SQL, гүйцэтгэлийн үр дүнгийн hash, зөв эсэх, хугацаа, token, алдааны төрлийг хадгал. Энэ нь paired тест ба алдааны шинжилгээнд хэрэгтэй.
- Ач холбогдлын тест. Хоёр тохиргоог ижил асуултууд дээр McNemar тестээр харьцуул. Жишээ нь 300 асуултаас 30 нь зөрүүтэй бол шинэ тохиргоо дор хаяж 11-ээр илүү (~3.7 оноо) байж p < 0.05 болно.
- Тохиргоог батлах шалгуур. Dev дээр ач холбогдолтой ахиц, англи ба галиг дээр 2-оос дээш онооны уналтгүй, p95 хугацаа төсөвт багтсан.
- Алдааны шинжилгээ. Бүлэг бүрийн шилдэг тохиргооноос 50 алдааг NL2SQL-BUGs-ийн ангилал болон монгол тэмдэглэгээгээр ангил: утгын бичлэг, дагавар, галиг, нэр томьёо, буруу хүснэгт.

### Ажлын орчин
- Serving. Хоёр загварыг vLLM-ээр OpenAI-compatible API болгон ажиллуулж, нэг harness хоёуланг нь дуудна.
- GPU. BF16 жин Arctic-д ~15 GB, sqrl-9b (10B параметр)-д ~20 GB, дээр нь KV cache. 24 GB GPU дээр нэг удаад нэгийг, 40–80 GB дээр хоёуланг багтаана. FP8 зэрэг quantization хэрэглэвэл бүх run-д ижил байлга эсвэл BF16-тай харьцуулж хэмж.
- DB. Туршилтыг read-only replica эсвэл snapshot дээр, асуулга тутамд timeout-тайгаар ажиллуул.
- Орчуулга (A4). Apache лицензтэй LLM (жишээ нь Qwen3.5) хэрэглэ; NLLB-200 нь CC-BY-NC тул арилжааны зорилгод тохирохгүй.
- Log. MLflow (нээлттэй эх) эсвэл JSONL + энэ хүснэгт.
- SFT ба GRPO. Unsloth, LLaMA-Factory, ms-swift. GRPO-д rollout сервер ба сургалт зэрэг ажилладаг тул 80 GB-ийн GPU хэрэгтэй.
## Хугацаа ба GPU нөөц (L4)
Нэг L4 дээр сургалтгүй тест (A, B, E, F бүлэг, хоёр загвар) ~50 GPU-цаг буюу ~3 хоног болно. Сургасан загваруудын тестийг нэмбэл бүх тест ~90 GPU-цаг (~5 хоног); нэг тест (300 асуулт) 15–30 минут.
Fine-tune-тэй бүх 41 туршилтыг зөвхөн нэг L4-өөр хийвэл ~9.5 долоо хоног болох бөгөөд sqrl-9b-ийн RAG-тай SFT, GRPO 24 GB-д багтахгүй. Тестийг L4, сургалтыг цагаар түрээсэлсэн A100 80 GB дээр хийвэл бүгд ~23 хоногт (3.3 долоо хоног), хасагдсан төлөвлөгөөгөөр 13–15 хоногт дуусна. Зардал ~$310–650 тул гол хязгаар нь мөнгө биш, цаг.
Тооцооны таамаглал:
- Dev set 300 асуулт; prompt RAG-гүй ~3,000, RAG-тай ~5,000 токен; хариулт 600–800 токен (sqrl-ийн олон алхмыг оруулаад).
- vLLM batching; Arctic BF16, sqrl FP8. sqrl-ийг 24 GB-д BF16-аар ажиллуулбал KV cache-д зай бага тул 2–6 дахин удаан.
- SFT нь LoRA, L4 дээр ~700–850 токен/с; A100 ~2.5, H100 ~6–8 дахин хурдан.
- Тест бүр алдаа засахаар ~1.3 удаа давтагдана; GPU 75% ачаалалтай (үр дүн шалгах, шийдвэр гаргах завсартай).
- Хугацааг dev set, орчуулсан сургалтын өгөгдөл, RAG бэлэн болсон өдрөөс тоолсон; хүний ажил ороогүй.
- Эхний өдөр 50 асуулт, SFT-ийн 200 алхмаар бодит хурдаа хэмжиж, доорх тоог шинэчил.
### Нэг ажлын хугацаа
| Ажил | Arctic-R1-7B, L4 | sqrl-9b, L4 | A100 80 GB (хоёр загвар) |
| Тест, 300 асуулт (greedy) | 15–25 мин | 20–30 мин (FP8) | 3–5 мин |
| Тест, 8 хувилбарын санал хураалт (E2) | 1.5–2.5 цаг | ~3 цаг (FP8) | 20–35 мин |
| Rejection sampling, 5k асуулт × 8 (C1) | ~1 хоног | ~2 хоног | 5–9 цаг |

| SFT, RAG-тай prompt (D2) | ~1.7 хоног | багтахгүй | 16–19 цаг |
| GRPO (C6, C7, F4) | ~1.2 хоног, QLoRA-оор багтвал | багтахгүй | 10–12 цаг |

SFT нь 10k жишээ × 2 epoch, GRPO нь 2k асуулт × 8 rollout. Unsloth-ийн хэмжээгээр Qwen3.5-9B-ийн bf16 LoRA ~22 GB эзэлдэг бөгөөд Qwen3.5-д 4-bit QLoRA-г зөвлөдөггүй. GRPO-д rollout ба сургалт нэг GPU-д зэрэг багтах ёстой: 8B загвар 20K context, 8 гаргалттай үед ~54 GB (Unsloth).

### Хугацаа хэмнэх ба анхаарах зүйл
- Ablation-ыг жижгээр. C4, C5-ыг 5k жишээ, 1 epoch-оор ажиллуулбал ~4 дахин хурдан; зөвхөн ялсан тохиргоог бүтэн хэмжээгээр давт.
- Rejection sampling-ийг давтахгүй. D2-т C1-ийн гаргалтыг ашиглаж, зөвхөн prompt-д RAG нэм.
- Prompt-ыг богиносго. Сургалтын жишээнд зөвхөн хамааралтай хүснэгтийг үлдээвэл токен ~2 дахин цөөрч, SFT ~2 дахин хурдасна.
- sqrl-ийг FP8-аар. L4 дээр FP8-аар serve хийж, BF16-тай 50 асуулт дээр харьцуул; vision хэсгийг ачаалахгүй тохиргоог шалга.
- Сургалтын GPU. H100 (~$2–3 цаг тутамд) A100-аас ~2–3 дахин хурдан, нэг ажлын үнэ ойролцоо. Unsloth дээр Qwen3.5-ийн RL нь vLLM-гүй горимоор (fast_inference=False) явдаг тул sqrl-ийн GRPO-д rollout удаан байж болно.
- Зөвхөн L4 бол. 2 L4 түрээсэлж хоёр загварыг зэрэг явуулбал нийт хугацаа ~1.7 дахин богиносно.
- Өгөгдлийн нууцлал. Түрээсийн cloud сервер дээр харилцагчийн бодит өгөгдөл байршуулах нь хүний мэдээлэл хамгаалах хууль, дотоод журамтай зөрчилдөж болно. Сургалтыг нийтийн ба синтетик өгөгдлөөр cloud-д, бодит DB-ийн тестийг нууцалсан snapshot эсвэл дотоод сервер дээр хий.

## Одоогийн системийг солих шийдвэр
Шинэ систем одоогийнхыг ижил eval set, ижил metric дээр давж, shadow хугацаанд шинжээчдийн үнэлгээгээр илүү гарсан үед л солино.
1. Суурь оноо. Одоогийн системийг ижил 300 dev, 200 test асуултаар, ижил metric-ээр хэмж. Энэ бол шинэ системийн давах ёстой оноо.
2. Shadow горим. Шинэ ба хуучин систем бодит асуултад зэрэг хариулж, хэрэглэгчид хуучныхыг нь харуулна. Шинжээчид хоёр хариултыг харьцуулна.
3. Солих шалгуур. Test дээр кирилл EX хуучнаас ач холбогдолтой өндөр.Аюулгүй байдлын тест 100% хаагдсан.p95 хугацаа төсөвт багтсан.Shadow хугацаанд шинжээчдийн үнэлгээ хуучнаас дээр.
4. Буцаах зам. Хуучин системийг тодорхой хугацаанд унтраалгүй байлгаж, асуудал гарвал шууд буцна.
### Нээлттэй асуулт
- DB ямар engine вэ (PostgreSQL, MySQL, MS SQL, Oracle)? Хоёр загвар зөвхөн SQLite дээр сургагдсан тул A6, A7-г хийх эсэх үүнээс шалтгаална.
- Схем хэдэн хүснэгт, баганатай вэ? Prompt-д багтахгүй бол B10-ыг хийнэ.
- Одоогийн системийн log эсвэл бодит асуултууд байгаа юу? Eval set-ийг тэдгээрээс бүрдүүлэх нь хамгийн сайн.
- Fine-tune-д ямар GPU байгаа вэ? C, D бүлгийн хэмжээг үүнээс тогтооно.
