# Монгол хэл дээрх Text2SQL: судалгаанд суурилсан бүтээх заавар
 · 
## Товч хураангуй
Монгол хэлний text2sql-ийг эхнээс нь сургах шаардлагагүй. Англиар сайн сургагдсан 7–9B загвар дээр мэдлэгийн давхарга, утгын хайлт, алдаа засах давталт нэмээд бага хэмжээний монгол өгөгдлөөр LoRA fine-tune хийх нь судалгаагаар хамгийн их үр өгдөг.
- Эхлээд мэдлэг, дараа нь загвар. Databricks Genie-д зөвхөн тайлбар, жишээ SQL, дүрэм нэмснээр 13 асуултын зөв хариулт 0%-аас 100% хүрсэн. LinkedIn-д зөвхөн схем өгөхөд сайн үнэлгээтэй хариулт 9%, бүрэн мэдлэгтэй үед 48% байсан.
- Заавал байх гурван хэсэг. DB-ийн утга хайх (+2–3 оноо), гүйцэтгэлийн алдаагаар засах (+1–7 оноо), төстэй жишээ сонгох (санамсаргүй жишээнээс +2–4 оноо).
- Schema linking-ийг зөвхөн схем prompt-д багтахгүй үед хэрэглэ. Багтах бол тайлбартай бүтэн схемээ өг.
- Англиас бусад хэлэнд нарийвчлал 3–16 оноогоор унадаг. Хамгийн их уналт япон, турк шиг SOV, залгамал хэлэнд гардаг. Монгол хэл энэ бүлэгт багтана, гэхдээ уналтыг нь хэмжсэн судалгаа алга.
- Цөөн жинхэнэ монгол жишээ зөрүүний ихэнхийг нөхдөг. XSemPLR-д зорилтот хэлний 10% өгөгдөл оноог 31.97-оос 56.18 болгосон бол бүтэн өгөгдөлтэй үед 58.16.
- Схемийг англиар үлдээж, монгол тайлбар, синоним нэм. Хүний хүчийг утга агуулсан асуултын орчуулгад зарцуул.
- Fine-tune: CoT-тэй SFT, дараа нь execution reward-тэй GRPO. RL нь SFT дээр BIRD-dev-д 2.5–5 оноо нэмдэг. Англи өгөгдлийг заавал хольж үлдээ: зөвхөн монгол instruction-оор сургахад Gemma-2-9B-ийн монгол математикийн оноо 46.4-өөс 14.0 болсон (NLP2025).
- Хандалтын хяналтыг өгөгдлийн сангаар хий. Prompt дахь хязгаарлалтыг туршилтад 30 оролдлогоос 30-д нь тойрсон.
- Шийдвэрээ өөрийн аудитлагдсан eval set дээр гарга. BIRD Mini-Dev-ийн 52.8%-д gold SQL алдаатай байсан (Jin нар, 2026).
## 1. Text2SQL системийн ерөнхий бүтэц
Орчин үеийн text2sql нь нэг prompt биш: асуултыг хэвийн болгох, мэдлэг хайх, SQL үүсгэх, шалгаж засах гинж юм. 7–14B on-prem загварт хамгийн их нотолгоотой хэсгүүд нь мэдлэгийн давхарга, утгын хайлт, гүйцэтгэлийн алдаагаар засах давталт.
[EMBED caption=Text2SQL-ийн бүтэц · 6 алхам, 2 давталт ref=node/54142791-68a2]
Асуулт зүүн талын зургаан алхмаар дамжина. Цэнхэр нь хамгийн их оноо нэмдэг хэсгүүд бөгөөд хэрэглэгчийн зөвшөөрсөн SQL мэдлэгийн давхаргыг тасралтгүй баяжуулна.
Liu нарын тойм энэ гинжийг урьдчилсан боловсруулалт (schema linking, DB утга, нэмэлт мэдлэг), үүсгэлт, дараах боловсруулалт (засах, санал хураах, дахин эрэмбэлэх) гэж ангилдаг. Доорх 7 хэсэг нь Uber, Pinterest, LinkedIn, Snowflake-ийн систем болон судалгааны ablation-д суурилсан.
1. Мэдлэгийн давхарга (урьдчилан бэлдэх). Хүснэгт, баганын монгол тайлбар ба синоним, бизнес нэр томьёо, баталгаажсан асуулт–SQL жишээ, утгын индекс. Pinterest-д хүснэгтийн баримт нэмснээр зөв хүснэгт олох нь 40%-аас 90% болсон. Snowflake Cortex Analyst semantic model-оор дотоод 150 BI асуултад 90%-иас дээш авсан бол ганц prompt-той GPT-4o 51% авсан.
2. Хэвийн болгох ба intent. Галигаар бичсэн асуултыг кирилл түлхүүр рүү хувиргаж, асуулт аль сэдвийн хүснэгтүүдэд хамаарахыг тогтооно (Uber QueryGPT-ийн workspace). Тодорхойгүй асуултад нэг тодруулах асуулт асууж эсвэл татгалзана. Чөлөөт олон алхамт яриа одоогоор шийдэгдээгүй: BIRD-Interact-д GPT-5 даалгаврын 8.67%-ийг ярианы горимд, 17.00%-ийг agent горимд л гүйцэтгэсэн.
3. Хайлт (RAG). Схем, DB утга, жишээ, нэр томьёог тусдаа индексээс хайна. Дэлгэрэнгүйг 2-р хэсэгт.
4. SQL үүсгэх. Text2SQL-д тусгайлан сургасан эсэх нь хэмжээнээс чухал: on-prem судалгаанд Qwen2.5-Coder-7B 39.05, CodeLlama-34B 24.51 авсан. XiYan-SQL-ийн SQL fine-tune 7B-г 50.39-өөс 60.10, 14B-г 55.28-аас 63.95 болгосон. Схемийн нэг форматыг тогтоо: XiYanSQL-QwenCoder-7B нь M-Schema-тай 62.13, DDL-тэй 57.43 авсан.
5. Шалгах ба засах давталт. SQL-ийг parse хийж, EXPLAIN-ээр шалгаад, зөвхөн уншиж гүйцэтгэнэ. Алдаа гарвал мессежийг нь буцааж өгөөд 1–3 удаа засуулна. On-prem судалгаанд энэ нь Qwen2.5-Coder 7–32B-д 1.24–3.45 оноо нэмж, 1,000 асуулгын өртгийг $0.123-аас $0.215 болгосон. Энэ хэсгийг хасахад MAC-SQL 4.63, CHESS 6.80, CHASE-SQL 3.78 оноо алдсан.
6. Олон хувилбар ба сонголт (сонголттой). Ерөнхий загварт нэг prompt-оор олон удаа үүсгэж санал хураах нь бараг ашиггүй: 5 дахин их token-оор +0.13 оноо, p95 хугацаа 10.6-аас 50.0 секунд болсон. RL-ээр сургасан загварт ашигтай: sqrl-9b 8 хувилбараар 66.6-аас 69.8 болсон. 8 хувилбар бүгд ижил үед (асуултын ~60%) хариулт ~87% зөв тул санал нийлэлтийг итгэлийн дохио болгож, зөрвөл хүнд шилжүүл.
7. Хариулт. Үр дүн, SQL, асуултыг хэрхэн ойлгосныг монголоор харуулна (Snowflake, Uber). Хэрэглэгчийн зөвшөөрсөн SQL жишээний санд орж, мэдлэгийн давхарга тасралтгүй өснө.
Хурд ба зардал. Сургалтгүй DeepEye-SQL Qwen3-Coder-30B-A3B-тэй BIRD dev-д 73.5, test-д 75.07 авсан; нэг асуулт ~17.8 секунд, ~23 мянган оролтын token. Ижил хэмжилтээр CHESS 284 секунд, Alpha-SQL 377 секунд зарцуулдаг. Leaderboard-ын оргил Agentar-Scale-SQL (test 81.67) нэг асуултад 56–172 LLM дуудлага, хаалттай загвар хэрэглэдэг тул on-prem-д DeepEye-SQL хамгийн ойр жишээ.
Аж ахуйн нэгжийн бодит байдал. Spider 2.0-д o1-preview agent даалгаврын 21.3%-ийг шийдсэн бол Spider 1.0-д 91.2%. Тиймээс загварт түүхий warehouse биш, сонгож тайлбарласан view, data mart өг.
## 2. RAG давхарга: юуг, яаж хайх вэ
Text2SQL-ийн RAG бол баримт бичиг хайх биш, дөрвөн тусдаа индекс: бизнес нэр томьёо, схем, DB утга, баталгаажсан жишээ. Хамгийн их нөлөөтэй нь бизнес мэдлэг: BIRD-д нэр томьёоны тайлбар (evidence) өгөхөд GPT-4-ийн test EX 34.88-аас 54.89 болж 20 оноо өссөн.
| Индекс | Юу хадгалах | Хайх арга | Хэдийг авах | Нотолгоо |
| Бизнес нэр томьёо, метрик | Нэр томьёо кирилл, галиг, англиар; тодорхойлолт; SQL илэрхийлэл; холбоотой багана; бусад нэр томьёоны хамаарал | Hybrid (BM25 + embedding), дараа нь хамаарлаар нь дагаж авах | 3–5 | SEED-ийн автомат evidence CodeS-7B-г 41.92-оос 56.58 болгосон |
| Схем | Англи identifier; монгол тайлбар, синоним (кирилл, галиг); төрөл; PK/FK; баганын 2 жишээ утга | Identifier, синоним дээр BM25 + тайлбар дээр embedding. LLM-ээр хэрэгтэй англи нэрийг эхлээд таамаглуулна (CRUSH4SQL) | ~6 хүснэгт × 10 багана + FK хөршүүд (CodeS) | Pinterest: баримттай үед хүснэгт олох 40% → 90% |
| DB утга | Текст баганын давтагдашгүй утгууд (салбар, дүүрэг, бүтээгдэхүүн), хоёр түлхүүрээр хэвийн болгосон | Character n-gram BM25 эсвэл MinHash-LSH, дараа нь LCS / edit distance-ээр дахин эрэмбэлэх (CodeS, CHESS) | Түлхүүр үг бүрд 10 нэр дэвшигч → багана бүрд 1–2, нийт 10–20 | Хасахад CodeS-7B 2.48, CHASE-SQL 2.92, DeepEye-SQL 2.1 оноо алдсан |
| Баталгаажсан жишээ | Асуулт (кирилл, галиг), нэр ба утгыг placeholder болгосон асуулт, SQL, SQL-ийн бүтэц (skeleton) | Placeholder-тэй асуулт дээр embedding, дараа нь SQL бүтцээр дахин эрэмбэлэх (DAIL-SQL) | 3–5 | GPT-4, Spider dev: DAIL сонголт 81.7, санамсаргүй 79.4, жишээгүй 72.3 |
### Schema linking хэзээ хэрэгтэй
- Схем prompt-д багтах бол тайлбартай бүтэн схемээ өг. The Death of Schema Linking? судалгаанд шүүлтүүр асуултын 10–23%-д хэрэгтэй баганыг хассан тул fine-tune хийсэн GPT-4o pipeline 4.77–11.57 оноо алдсан. On-prem судалгаанд 96.5% recall-тай embedding linker ч ашиг өгөөгүй.
- Сул загварт богино, эрэмбэлсэн схем тустай. Llama-3.1-8B шүүлтүүрээс ашиг хүртсэн. RESDSQL-ийн жижиг загвар эрэмбэлээгүй бүтэн схемтэй 77.9-өөс 70.1 болж унасан. 7–9B загвар энэ хоёрын дунд байдаг тул өөрийн dev set дээр бүтэн ба товчилсон схемээр A/B туршилт хий.
- Схем том бол recall-ыг (≥95%) тэргүүнд тавь. RSL-SQL баганын 83%-ийг хасаад 94% strict recall хадгалж, бүтэн ба товчилсон схемийн хариултыг гүйцэтгэлээр нь харьцуулж сонгодог.
- Олон DB бол эхлээд DB чиглүүлэгч сурга. DBCopilot 80 DB-ээс зөвийг эхний байрт 88.92% олсон бол BM25 57.11%. Warehouse хэмжээнд олон шаттай хайлт хэрэгтэй: LinkAlign Spider 2.0-Lite дээр 33.09% авсан.
### Монгол утга ба латин галиг
- Утга бол кирилл, нөхцөлтэй хэлний хамгийн хэцүү хэсэг. PAUQ-д орос хэлний WHERE нөхцлийн алдаа 0.55–0.57 байсан бол англид 0.23–0.31.
- Асуулт ба индексийг ижил хоёр түлхүүрээр хэвийн болго. Кирилл түлхүүр: жижиг үсэг, Unicode NFC. Сул латин түлхүүр: кириллийг тогтмол схемээр латин болгож, хувилбаруудыг нэгтгэнэ (kh/h→h, ts/c→c, ө/о→o, ү/у→u, давхар эгшиг→дан, ь/ъ хасах). Хэрэглэгчийн бодит бичлэгийг өөрийн query log-оос гарга.
- Үгийг бүтнээр нь биш, хэсгээр нь тааруул. Character n-gram, substring, LCS ашиглавал «Улаанбаатарт», «Улаанбаатараас», «Улаанбаатарын» бүгд «Улаанбаатар»-т очно.
- Цөөн утгатай баганын бүх утгыг схемд шууд бич. Төлөв, бүтээгдэхүүний төрөл гэх мэт баганад Snowflake-ийн is_enum шиг жагсаалт өгнө.
- Хувийн мэдээллийг индексжүүлэхгүй. Регистр, утас, дансны дугаарыг оруулахгүй; харилцагчийн нэрийг зөвхөн row-level security-ийн ард. Утгын индексийг DB шиг хамгаал.
- Скрипт хооронд утга тааруулахыг шалгасан судалгаа олдсонгүй, тиймээс үүнийг өөрийн eval set-ээр хэмж.
### Жишээ сонгох
- Embedding хийхийн өмнө нэр, утгыг placeholder болго: DAIL-SQL-д placeholder-тэй 81.5, placeholder-гүй 79.2.
- Fine-tune хийсэн загварт жишээний ашиг буурдаг (DAIL-SQL), тиймээс өөрийн загвар дээр жишээтэй, жишээгүй хувилбарыг харьцуул.
- Жишээний санг хэрэглэгчийн зөвшөөрсөн асуулгаар өсгө (Vanna, Snowflake verified_queries).
### Embedding загвар
- Шалгасан загваруудаас зөвхөн LaBSE монгол хэлийг (mn) жагсаалтдаа нэрлэсэн. XLM-R-ийн CC-100 корпус 3.0 GiB монгол текст агуулсан тул multilingual-e5 зэрэг XLM-R суурьтай загварууд монгол хэл үзсэн.
- Qwen3-Embedding (0.6B / 4B, Apache 2.0), BGE-M3 (MIT) 100+ хэл гэдэг ч жагсаалт өгөөгүй. jina-embeddings-v3 нь CC BY-NC тул арилжааны зорилгоор бүү ашигла.
- Эхлээд MTEB-ийн BelebeleRetrieval-ийн khk_Cyrl хэсгээр шүүж, дараа нь өөрийн өгөгдлөөр (галиг асуулт, кирилл нэр томьёо, англи баганын тайлбар) шалга.
Хэрэгслийн загвар. Snowflake Semantic View YAML (синоним, жишээ утга, is_enum, verified_queries) нь on-prem semantic YAML-д сайн загвар болно. Vanna-гийн DDL, баримт, асуулт–SQL гэсэн гурван индексийн бүтцийг хуулж болох ч репо 2026-03-29-нд архивлагдсан тул түүн дээр бүү бүтээ.
## 3. Fine-tuning: SFT, дараа нь RL
Ажлын жор: сайн text2sql checkpoint-оос эхэлж, гүйцэтгэлээр баталгаажсан 10–50 мянган CoT жишээгээр SFT хийгээд, дараа нь execution reward-тэй GRPO хий. RL нь сайн SFT загвар дээр BIRD-dev-д 2.5–5 оноо нэмдэг: Arctic-Text2SQL-R1-7B 63.9-өөс 68.9, sqrl-9b 64.0-өөс 66.6 болсон.
### Судалгааны гол олдворууд
- Эхлэх checkpoint ба prompt формат хамгийн чухал. Arctic-32B-г OmniSQL-оос эхлүүлж, түүний prompt-ыг хэрэглэхэд 67.9-өөс 70.5 болсон; reasoning загвар QwQ-32B-ээс эхлэхэд ердөө 55.2. Сургалт ба ашиглалтад яг ижил prompt, схемийн формат хэрэглэ.
- CoT ба синтетик өгөгдөл тусалдаг, гэхдээ шүүх ёстой. OmniSQL-7B-ийн ablation (BIRD-dev): CoT-гүй 55.1, CoT-той 59.6, SynSQL нэмэхэд 63.9. Arctic-14B шүүгээгүй синтетиктэй 64.6, шүүсэнтэй 66.5, синтетикгүй 64.9.
- Нэг benchmark дээрх SFT бусад өгөгдөлд шилжих чадварыг эвддэг, RL эвддэггүй. Reasoning-SQL 7B-ийн Spider оноо BIRD дээр SFT хийсний дараа 77.85-аас 68.08 болж унасан бол GRPO-ийн дараа 78.72.
- ≥7B загварт энгийн execution reward хангалттай. Arctic: үр дүн таарвал 1, SQL зүгээр ажиллавал 0.1, бусад 0; нарийн reward загварыг «залхуу» болгосон. Databricks: 0/1, буруу SQL −1. Харин 4B-д gated dense reward тусалсан: Think2SQL 4B 49.0-өөс 59.6.
- Дохио өгөх асуултаар сурга. Arctic 10 оролдлогоос дор хаяж 1 нь зөв байсан синтетик асуултыг л үлдээсэн; SQRL заримдаа л шийддэг асуултуудаар RL хийсэн.
- DPO нь RL-ийн хямд хувилбар, гэхдээ CoT шаарддаг. ExCoT Qwen2.5-Coder-32B: суурь 58.93, SFT 59.65, off-policy DPO 66.23, on-policy DPO 68.25. CoT-гүй DPO ердөө 2.6 оноо нэмсэн.
- Монгол хэлний онцгой эрсдэл. Монгол Alpaca-аар instruction tune хийхэд Gemma-2-9B-ийн монгол математик (MonGSM) 46.4-өөс 14.0, Llama-3.1-8B-ийнх 34.0-өөс 4.0 болж унасан (NLP2025). Англи болон SQL өгөгдлөө үргэлж хольж, монгол ерөнхий чадварыг алхам бүрийн өмнө, дараа хэмж.
- Gold label-ийг цэвэрлэ. BIRD-ийн албан ёсны шүүсэн train 9,428-аас 6,601 (~70%) жишээ үлдээсэн.
### Үе шаттай жор (7–9B, 1–4 GPU)
1. Checkpoint сонгох. sqrl-9b эсвэл Qwen3.5-9B, Arctic-Text2SQL-R1-7B эсвэл OmniSQL-7B-г монгол dev set дээр харьцуулж сонго. Instruct ба text2sql-д тусгайлсан загвар нь base эсвэл reasoning загвараас илүү эхлэл болдог (Arctic).
2. SFT өгөгдөл: 10–50 мянга, гүйцэтгэлээр баталгаажсан, CoT-той. Цэвэрлэсэн англи асуултуудын монгол орчуулга (BIRD23-train-filtered 6,601; хоосон эсвэл 5 секундээс удаан gold-ыг хассан Spider), SQL-ийг өөрчлөхгүй.Өөрийн схем дээр OmniSQL маягийн синтез: SQL-ийг 4 түвшний нарийн төвөгтэйгээр үүсгэж, монгол асуулт руу буцааж орчуулна (OmniSQL 9 хэв маяг ашигласан). CoT-ыг гүйцэтгэлийн олонхоор баталгаажуулна.Хэцүү асуултад багш загвар gold SQL-ийг харж CoT бичнэ; гүйцэтгэл таарсныг үлдээж, gold-ыг шууд хуулсныг хасна (ReToolSQL).Англи эх өгөгдлийн 30–50%.Жишиг хэмжээ: SQRL ~10.2 мянга, ExCoT ~11.7 мянга, ROUTE 45.5 мянга.
3. GRPO (санал болгож буй) эсвэл DPO (хямд). GRPO-д 5–20 мянган асуулт аваад, загвар заримдаа шийддэгийг нь үлдээ. Кирилл ба галиг асуулт хоёуланг оруул. Checkpoint-ыг BIRD биш, монгол dev set-ээр сонго.
4. Serving. 4–8 хувилбарын санал хураалт хийж, санал нийлэлтээр итгэл тооцоод, зөрвөл татгалзах эсвэл хүнд шилжүүл.

## 5. Монгол хэлэнд зориулсан алхам алхмаар төлөвлөгөө
Эхлээд хэмжилт, дараа нь мэдлэг ба хайлт, хамгийн сүүлд fine-tune: судалгаагаар хямд, өндөр өгөөжтэй алхмууд эхэнд байна. Үе шат бүрийн шалгуурыг давсны дараа дараагийнх руу шилж.

Доорх алхам бүр диаграммын үе шаттай таарч, юу хийхийг дэлгэрэнгүй заана.
1. Eval set ба baseline. Өөрийн схем дээр 300–500 бодит асуулт цуглуул (query log, шинжээчдийн асуулт). Gold SQL-ийг гүйцэтгэлээр шалгаж, хоёр хүн баталгаажуул.Асуулт бүрийг кирилл, латин галиг, англи хувилбартай болго. Англи хувилбар хэлний зөрүүг хэмжинэ.10–15% хариултгүй, 10–15% хоёрдмол утгатай асуулт оруул.2–3 загварыг (жишээ нь sqrl-9b, Arctic-Text2SQL-R1-7B, Kwai-AutoSQL-14B; суурь болгон Qwen3.5-9B, Gemma 4) шууд монголоор ба «эхлээд англи руу орчуулах» горимоор турш.Шалгуур: загвар бүрийн суурь оноо ба монгол–англи зөрүү тогтсон.
2. Мэдлэгийн давхарга ба RAG. Semantic YAML бэлд: хүснэгт, баганын монгол тайлбар, синоним (кирилл, галиг), «идэвхтэй зээл», «хугацаа хэтэрсэн» зэрэг нэр томьёоны SQL тодорхойлолт.Хоёр түлхүүртэй утгын индекс, 100–300 баталгаажсан асуулт–SQL-тэй жишээний сан бүрдүүл.Шалгуур: eval set дээр хэрэгтэй хүснэгт ба утгын recall ≥95%, EX baseline-аас өссөн.
3. Шалгалт, засвар, татгалзах зам. sqlglot parse, allow-list, EXPLAIN, read-only гүйцэтгэл, алдаагаар 1–3 удаа засах давталт.4–8 хувилбарын санал нийлэлтээр итгэл тооцож, TrustSQL маягийн торгуулийн оноогоор татгалзах босгыг тохируул.Шалгуур: SQL-ийн ≥95% ажилладаг, injection тест бүгд хаагдсан.
4. Монгол өгөгдөл ба LoRA SFT. BIRD23-train-filtered, Spider, SynSQL-ийн хэсгийг BIRDTurk-ийн аргаар монгол руу орчуул. SQL-ийг өөрчлөхгүй, англи ба орчуулгын SQL ижил үр дүн өгөхийг шалгаж, ~1,000 жишээг хүнээр шалга.Өөрийн схем дээрх синтез, хүний бичсэн 1–2 мянган монгол жишээ, 30–50% англи өгөгдлийг холь.Лиценз: BIRD нь CC BY-SA 4.0 тул түүнээс гаргасан орчуулгыг түгээх бол ижил лицензээр; SynSQL-2.5M нь Apache 2.0.Шалгуур: монгол dev өссөн, англи EX ба монгол ерөнхий чадвар унаагүй.
5. GRPO. Execution reward, кирилл ба галиг асуулт, загвар заримдаа л шийддэг асуултууд.Шалгуур: монгол dev дээр нэмэлт ахиц (судалгаанд +2.5–5 оноо).
6. Pilot ба сайжруулалтын давталт. Шинжээчидтэй shadow горимоор ажиллуулж, сонгосон хүснэгт ба SQL-ийг харуул.Сөрөг тохиолдол бүрийг eval set ба жишээний санд нэмж, 2-р алхам руу буц.Шалгуур: Databricks хэрэглэгчийн туршилтыг ихэвчлэн 80%-иас дээш оноотой үед эхлүүлдэг; өөрийн босгыг ашиг ба эрсдэлээр тогтоо.

## 6. Үнэлгээ: eval set, metric, алдааны ангилал
Шийдвэрээ нийтийн leaderboard биш, өөрийн аудитлагдсан 300–1,000 асуулттай монгол eval set дээр гарга. Шинжээчид BIRD Mini-Dev-ийн 52.8%, Spider 2.0-Snow-ийн 62.8%-д gold алдаа олсон бөгөөд засварын дараа agent-уудын эрэмбэ 9 хүртэл байраар өөрчлөгдсөн (Jin нар, 2026).
### Metric
- Гол metric: test-suite execution accuracy. Gold ба гарсан SQL-ийг бодит өгөгдлийн хуулбар болон NULL, тэнцүү утга, хязгаарын утга, хоосон үр дүнтэй 5–20 синтетик хуулбар дээр ажиллуулна. Ганц DB дээрх EX буруу асуулгыг дунджаар 6.5%, хамгийн хэцүү асуултад 11.0% зөвшөөрдөг (Zhong нар, 2020).
- LLM шүүгч. EX хүний шүүлттэй ердөө 81% санал нийлсэн. Хүнтэй тохирох зэрэг (κ) нь GPT-4o суурьтай FLEX-д 87.04, EX-д 62.00. Local шүүгчийг дор хаяж 200 хүний үнэлгээтэй хос дээр шалгаж байж хэрэглэ.
- Найдвартай байдлын оноо. Зөв хариулт ба зөв татгалзалт +1, хариулж болохыг татгалзвал 0, буруу хариулт −c (c = 10-аас эхэл). TrustSQL-д бүгдийг татгалзах нь 50 оноо авдаг бөгөөд c = 10 үед ихэнх систем түүнээс доогуур.
- Хоёрдмол утга. Зорилготой тодруулах асуулт асуусан эсвэл бүх тайлбарын SQL-ийг гаргасан бол зөвд тооц. AMBROSIA-д Llama 3-70B хоёрдмол асуултын тайлбарын 30.7%-ийг, тодорхой асуултынхаа 64.5%-ийг олсон.
- Оношилгооны metric. Ажилладаг SQL-ийн хувь, хоосон үр дүнгийн хувь, хүснэгт ба баганын recall, хугацаа, Soft-F1.
- Өөрийн dialect дээр хэмж. BIRD Mini-Dev-д Llama3-70B SQLite дээр 40.80, PostgreSQL дээр 29.40 авсан.

### Хэмжээ ба статистик
70% нарийвчлалтай үед 95%-ийн итгэлийн алдаа n = 200-д ±6.4, n = 400-д ±4.5, n = 1,000-д ±2.8 оноо. 300–500 асуултаар эхэлж ~1,000 болго, хувилбаруудыг ижил асуултууд дээр McNemar тестээр харьцуул. Uber ~5%-ийн хэлбэлзлийг дуу чимээ гэж үздэг.
### Gold SQL хоёрдмол үед
Нэг асуултад хэд хэдэн зөв gold SQL эсвэл үр дүнг зөвшөөр: LinkedIn-ий асуултын 60% нь нэгээс олон зөв хариулттай байсан. Хоёр хүнээр тэмдэглүүлж, нэр томьёоны толь ашигла. Бүх хувилбар унасан асуултын gold-ыг дахин шалгаж, eval set-ээ хувилбарлан хадгал.
### Алдааны ангилал
Алдаа бүрийг NL2SQL-BUGs-ийн 9 ангиллаар тэмдэглэ: attribute, table, value, operator, condition, function, clause, subquery, бусад. LLM алдааг дунджаар 75.16%-д нь л илрүүлдэг тул хүний шалгалт хэрэгтэй.
### Давтамж
- Загвар, prompt, индекс, схемийн баримт, validator өөрчлөгдөх бүрт бүтэн suite-ийг release gate болгон ажиллуул.
- Долоо хоног бүр production асуултаас дээж ав; сар бүр log ба сөрөг feedback-ээс шинэ асуулт нэм.
- Улирал бүр gold-оо аудитла; схем өөрчлөгдсөн даруйд дахин ажиллуул.
## 7. Production: аюулгүй байдал, хяналт, сайжруулалт
Хандалтын хяналтыг prompt-оор биш, өгөгдлийн сангаар хий: P2SQL туршилтад GPT-3.5 дээр prompt дахь унших, бичих хязгаарлалтыг 30 оролдлогоос 30-д нь тойрсон. Бодит системүүд шинжээчийг орлох биш, туслах байдлаар амжилттай ажиллаж байна.
### Хамгаалалт
- Bot-д тусдаа DB role өг: зөвхөн сонгосон view дээр SELECT; table owner, superuser, BYPASSRLS биш.
- Row-level security-г эцсийн хэрэглэгчээр (салбар, зээлийн багц) тохируулж, FORCE ROW LEVEL SECURITY асаа (PostgreSQL RLS).
- SQL бүрийг зөв dialect-тай sqlglot-оор parse хий: ганц SELECT (WITH…SELECT) зөвшөөрч, DDL, DML, COPY, SET, pg_sleep, dblink, lo_*-г хориглож, хүснэгт ба баганыг allow-list-ээр шалга. sqlglot өөрөө validator биш тул зөвхөн эхний шүүлтүүр болно.
- Гүйцэтгэхээс өмнө EXPLAIN ба каталогийн шалгалт хийж, 1–2 удаа засуул. LinkedIn ийм шалгалтаар асуулгын 96%-ийг compile болгож, 99%-д зөв identifier хэрэглэсэн.
- LIMIT болон заавал байх шүүлтүүрийг query rewrite-аар хүчлэ (асуулга бүрт ~1.87 ms).
- Role бүрд statement_timeout, lock_timeout, idle_in_transaction_session_timeout тохируулж, read replica дээр ажиллуулж, EXPLAIN-ийн өртөг өндөр асуулгыг татгалз.
- DB доторх чөлөөт текстийг (зээлийн зорилго, гомдол) итгэмжгүй оролт гэж үз: P2SQL-д шууд бус injection chain горимд 100%, agent горимд 60% амжилттай байсан.
- Регистр, утас, дансны дугаарыг view-д нууцалж эсвэл хасаж, tag-тай баганыг загварт харагдах схемээс хас. Log-ийг шифрлэж, хадгалах хугацааг хязгаарла.
- Хүсэлт бүрд audit log хөтөл: хэрэглэгч, асуулт, context, SQL, validator-ийн шийдвэр, хугацаа, мөрийн тоо, feedback.
- Release бүрийн өмнө P2SQL-ийн халдлагын prompt-уудыг монгол, галигаар орчуулж ажиллуул; DB ба validator 100%-ийг хаах ёстой.
### Хэрэглэгчийн туршлага
- Сонгосон хүснэгтийг хэрэглэгчид харуулж, засах боломж өг (Uber, Pinterest).
- Асуултыг хэрхэн ойлгосныг монголоор тайлбарлаж, SQL-ийг хамт харуул (Snowflake).
- Тодруулах ба татгалзах замыг TrustSQL маягийн оноогоор тохируул.
### Хяналт ба сайжруулалт
- Эерэг, сөрөг үнэлгээ, эхний оролдлогоор зөвшөөрсөн хувь, SQL-ийг editor руу хуулсан эсэхийг цуглуул.
- Сөрөг тохиолдол бүрийг eval set ба жишээний санд нэм; домэйны эзэд тайлбар, жишээ нэмэх боломжтой бай.
- Амжилттай гүйцэтгэл, хоосон биш үр дүн, intent-ийн нарийвчлал, хүснэгтийн давхцал, validator-ийн татгалзалт, latency-г хяна.
Бодит үр дүн. Pinterest-д эхний оролдлогоор зөвшөөрөх хувь 20%-аас 40% гаруй болж, SQL бичих 35% хурдассан. Uber-ийн QueryGPT нэг асуулгын хугацааг ~10-аас 3 минут болгож, pilot хэрэглэгчдийн 78% нь цаг хэмнэсэн гэжээ. LinkedIn-ий хариултын 53%-ийг шинжээчид 5-аас 4 ба түүнээс дээш гэж үнэлсэн.
