# R1. Орчуулгын шат ба бага нөөцтэй хэлний Text2SQL (2026-10-30)

Хамрах хүрээ: `pipeline/translate.py` (M1 = MADLAD-400-3B QLoRA, mn→en) → `orchestrator._question_for` (`translate_mode`) →
Arctic-Text2SQL-R1-7B. `docs/RESEARCH_NEXT.md` (§9–10), `docs/RESEARCH_TECH_2.md` (T9 — олон орчуулгын чуулга),
`docs/SQL_QUALITY_AND_GAP.md`-д бичигдсэнийг давтахгүй, зөвхөн тэдгээрийг нарийвчилж, шинэ аргыг нэмнэ.
Шинэ ишлэлийн BibTeX `docs/research_refs.bib`-д, түлхүүрийг `[...]`-д бичив. Тайлангийн `report_diplom/references.bib`-д аль
хэдийн байгаа ажлыг (MultiSpider, BIRDTurk, BIRD_PT, Self-Translate, MADLAD, chrF++ г.м.) тэр түлхүүрээр нь иш татав.
Зөвхөн хайлтын хураангуйгаар (хуудсыг бүтэн уншаагүй) олсон тоог **(баталгаагүй)** гэж тэмдэглэв. Test-ийн gold-ыг ашиглаагүй;
бүх «манай» тоо dev эсвэл тайлангийн Ch6-аас.

## 0. Одоогийн байдал (кодоос ба хэмжилтээс)

| Юу | Хаана | Баримт |
|---|---|---|
| Утга хамгаалах | `translate.find_value_spans` → `filter_spans` (T2, DB-ийн оноосон нэр) → `prepare_v2` «каноник» | regex нь зөвхөн бизнес түлхүүр, `UB01` код, `YYYY-MM-DD`, ишлэл. «2025 оны 3-р сар», «5 сая», «өнгөрсөн улирал» хамгаалагдахгүй |
| Нэр томьёо | `translate_terms.term_hints` (≤6 мөр), seq2seq-д `<2en> [T: …] асуулт` (`scripts/mt/m0_translate.py: HFSeq2Seq.translate`) | M1 нэр томьёо зөв 69.0% (Qwen 46.3%, dev-ийн жишиг англи 59.6%) |
| Decoding | `HFSeq2Seq._generate`: `num_beams=4`, зөвхөн 1-р гаралт | n-best хадгалдаггүй |
| Утгын хадгалалт | `unmark` — утга алдагдвал төгсгөлд `("утга")` нэмнэ, гэхдээ зөвхөн `--mark-values db` үед | M1: DB-ийн утгыг хадгалсан **13.6%** (n = 22), Qwen 63.6%. M1m («» тэмдэглэгээ) +2/−0, p = 0.5 |
| Загварт өгөх | M1a ← I3 ← H4: `translate_mode = en_prompt` (Arctic зөвхөн англи, retrieval монголоор) | H2 (монгол + англи) ≈ H4 (109 vs 110, dev, Qwen орчуулгатай) |
| Нэг асуултад нэг орчуулга | `orchestrator.translations[id:variant]` — нэг мөр | Олон орчуулгыг зөвхөн тусдаа кэш + `reselect --extra`-аар |
| Нөлөө | I3t → M1a: dev +9.8 хувь (+40/−18, p = 0.0054), test +12.6 хувь (+32/−13, p = 0.0066; test-ээс мэдээлэл авсан 13 асуултгүйгээр p = 0.047, загвар төстэй 6-г ч хасвал p = 0.16) | Орчуулга нь хамгийн том, батлагдсан ахицын эх үүсвэр |
| Алдааны хувь | E2 dev: хариулах боломжтой 124 буруугийн 47 нь орчуулгаас (маск 24, нэр томьёо 23) — Qwen үед | M1-ийн алдааны задаргаа хийгдээгүй (JSONL Kaggle-д) |

Дүгнэлт: M1 нэр томьёо ба chrF++-ээр сайн болсон. Үлдсэн эрсдэл: (а) утга/тоо/огноо хадгалалт, (б) нэг орчуулгад бүхэлдээ
найддаг (алдаа нь SQL-ийн бүх нэр дэвшигчид дамжина), (в) орчуулгын итгэлийг хэмждэггүй — муу орчуулгыг ялгаж чадахгүй.

| Sherborne нар [`sherborne_2020_bootstrapping`] | Герман, Хятад | Олон MT-ийн гаралтыг paraphrase маягаар чуулга болгох | Semantic parsing нь entailment-ээс илүү **баримтын нийцтэй байдал** (тоо, нэр) шаарддаг | Утга/тоо хадгалалт манайд хамгийн эмзэг (M1 13.6%) |

**Байр суурь (хамгаалалтад).** Монгол хэлэнд нээлттэй Text2SQL загвар, сан байхгүй (RESEARCH_NEXT §10). Arctic-R1-7B нь англи
өгөгдлөөр сургагдсан. Тиймээс translate-test + англи схем + монгол утга нь CSpider, Ar-Spider, AraSpider, BIRD_PT-тэй нэг
стратеги. Artetxe нарын дүгнэлтээр энэ стратегийн гол хөшүүрэг нь MT-ийн чанар — манай M1-ийн +12.6 хувь (test, p = 0.0066; 13 асуултгүйгээр p = 0.047, загвар төстэй 6-г ч
хасвал p = 0.16 — ач холбогдолгүй) үүнийг дэмждэг.
Шууд (орчуулгагүй) хувилбар манайд D2 fix (19.3%) < D2 tr (27.0%, ижил код) тул буцаж очих шалтгаангүй.

## 2. Аргууд (арга бүрээр)

### R1.1. Тоо, огноо, мөнгөн дүнгийн нормчлол + хамгаалалт (орчуулгын өмнө)

- **Эх сурвалж:** Sherborne нар [`sherborne_2020_bootstrapping`] (баримтын нийцтэй байдал); PAUQ [`bakshandaeva_2022_pauq`]
  (утгатай асуултыг тусгайлан засварласан); Dinu нар [`dinu_2019_terminology`] (inline тэмдэглэгээ).
- **Санаа:** «5 сая төгрөг», «1.2 тэрбум», «2025 оны 3-р сар», «2025 оны 1-р улирал», «30-аас дээш хоног» зэргийг орчуулахаас
  өмнө тогтмол хэлбэрт (`5000000 MNT`, `2025-03`, `2025 Q1`, `> 30 days`) хөрвүүлж «»-д хийнэ. Орчуулагч зөвхөн хуулна.
- **Нотолгоо:** Qwen-ийн тоо хадгалалт 95.0% (кирилл) — 5% нь тоо алдсан асуулт (`scripts/mt/baseline_dev.py`). M1-ийн тоо
  хадгалалтыг хэмжээгүй. Тоо/огноо алдсан асуултын SQL бараг үргэлж буруу (шүүлтийн нөхцөл — алдааны 22–25%).
- **Манай кодод:** `translate._PATTERNS`-д нэмэх: `\d+([.,]\d+)?\s*(мянга|сая|тэрбум)`, `(\d{4})\s*оны\s*(\d{1,2})-?(р|дугаар)\s*сар`,
  `(\d)-?(р|дүгээр)\s*улирал`. `prepare_v2`-д нормчилсон хэлбэрийг `canon`-д бичнэ. `scripts/mt/mt_metrics.digits_kept`-ээр
  M1 кэш дээр (dev) эхлээд хэмжинэ. Харьцангуй огноог («өнгөрсөн сар») хөрвүүлэхгүй — `abstain.py`-ийн `vague_time`-тэй зөрчилдөнө.
- **Анхааруулга:** M1 нь «»-тэй форматаар сургагдсан ч M1m туршилтад ялгаагүй байсан. Нормчилсон тоо M1-ийн сургалтын тархалтаас
  гадуур байж болно → эхлээд dev 300 дээр `digits_kept`-ээр шалгах.
- **Kaggle:** CPU-д regex; M1-ээр dev дахин орчуулах ≈10 мин (T4), SQL run ≈2–2.5 цаг (нэг үүсгэлт).
- **Хүлээгдэх ахиц:** dev-д 0…+3 асуулт **(баталгаагүй, таамаг)**. Тоо алдсан асуултын тоо бага (≈5%) тул дээд хязгаар бага.

### R1.2. Орчуулгын дараах тогтмол шалгалт (утга/тоо/нэр томьёо) → bilingual fallback

- **Эх сурвалж:** Moon нар [`moon_2020_rtt_qe`] (reference-гүй QE); манай `translate_fix.fix_record` (Qwen-д H2 fallback).
- **Санаа:** Орчуулгын дараа гурван шалгалт: (1) эх асуултын тоо бүр англид байна уу (`digits_kept`); (2) `filter_spans`-аар
  олдсон DB-ийн утга бүр (каноник хэлбэрээр) байна уу; (3) `term_hints`-ийн англи үг байна уу (`scripts/mt/term_accuracy.py`
  логик). Аль нэг нь унавал тухайн асуултад `translate_mode`-ийг `bilingual` болгоно (монгол асуулт + `(English translation: …)`),
  эсвэл алдсан утгыг `("Эрдэнэт салбар")` гэж төгсгөлд нэмнэ (`unmark`-ийн дүрэм).
- **Нотолгоо:** Qwen кэшийн masking засвар (`translate_fix`) I3 → I3t-д ахиц өгсөн (+33/−10 нь I3t-ийн бүх өөрчлөлт, зөвхөн
  засвар биш). H2 ≈ H4 (109 vs 110) тул fallback-ийн эрсдэл бага. M1-ийн утга хадгалалт 13.6% — шалгалт олон асуултыг барина.
- **Сул тал:** M1m (утгыг «»-ээр хамгаалах) +2/−0 л байсан нь утга алдагдал EX-д бага нөлөөлдгийг харуулж магадгүй (RAG нь
  монгол асуултаар утгыг олж prompt-д өгдөг). Тиймээс шалгалтын гол ашиг нь **тоо ба нэр томьёо** талд гэж үзнэ.
- **Манай кодод:** шинэ функц `translate.check_translation(source, text, mapping, hints) -> list[str]` ба
  `orchestrator._question_for`-д `translate_mode == "auto"` (асуулт бүрт шалгалтын үр дүнгээр en_prompt/bilingual). Кэшийн
  мөрт `checks` талбар нэмбэл GPU-гүйгээр кэш дээр урьдчилан тооцно.
- **Kaggle:** шалгалт CPU; SQL run ≈2 цаг (dev), эсвэл зөвхөн шалгалтад унасан асуултуудыг дахин ажиллуулж reselect-ээр нийлүүлэх
  (≈20–40 мин).
- **Хүлээгдэх ахиц:** +1…+4 асуулт (dev) **(баталгаагүй)**. Эрсдэл бага: шалгалт давсан асуултад өөрчлөлт байхгүй.

### R1.3. N-best орчуулга ба MBR (хамгийн «зөвшилцсөн» орчуулгыг сонгох)

- **Эх сурвалж:** Freitag нар [`freitag_2022_mbr`] — MBR decoding (нейрон хэмжүүрээр) нь beam-ийн хамгийн магадлалтай гаралтаас
  хүний үнэлгээгээр мэдэгдэхүйц сайн; загварын магадлал ба чанар «сул хамааралтай».
- **Санаа:** `num_beams=4` аль хэдийн ажиллаж байгаа тул `num_return_sequences=4` (эсвэл epsilon sampling 8) нэмэхэд зардал бараг
  нэмэгдэхгүй. N гаралтаас бусадтайгаа хамгийн өндөр дундаж chrF++ (`scripts/mt/mt_metrics.chrf`)-тэй нэгийг сонгоно (MBR,
  reference-гүй). Нэмж: n-best-ийн хоорондын санал нийлэлт бага бол (дундаж chrF++ < босго) «эргэлзээтэй орчуулга» гэж тэмдэглэнэ →
  R1.2-ын fallback руу.
- **Нотолгоо:** MT-д олон удаа батлагдсан (Freitag нар, WMT). Text2SQL-ийн EX-д нөлөө нь хэмжигдээгүй **(баталгаагүй)**. Манай
  M0-ийн жишээ: chrF++ ойролцоо байсан ч EX 10.7 хувиар бага — chrF++-ийн сайжрал EX-д шууд шилжихгүй.
- **T9(б)-ээс ялгаа:** T9(б) нь олон орчуулгыг **SQL-ийн чуулга** болгоно (SQL run ×N). Энд нэг л орчуулга сонгоно — SQL run нэг
  удаа. Хоёулаа нэг n-best кэшээс гарна.
- **Манай кодод:** `scripts/mt/m0_translate.py: HFSeq2Seq._generate`-д `num_return_sequences`, кэшийн мөрт `nbest: [...]`;
  `translate.py`-д `mbr_select(nbest) -> (text, agreement)`. Inference үйлчилгээнд (`translate_one`) мөн адил.
- **Kaggle:** n-best 4: dev 300 + latin 300 ≈ 10–15 мин (T4, NF4); MBR CPU. SQL run ≈2 цаг.
- **Хүлээгдэх ахиц:** 0…+3 асуулт **(баталгаагүй)**. Гол ашиг нь «agreement» оноо — R1.2, R1.4-д итгэлийн дохио болно.

### R1.4. Round-trip (буцаах орчуулга) ба cross-lingual ижил төстэй байдлаар итгэлийг хэмжих

- **Эх сурвалж:** Moon нар [`moon_2020_rtt_qe`] — RTT + семантик embedding-ээр QE нь WMT19-ийн QE-тэй өрсөлдөхүйц, буцаах
  орчуулагчийн сонголтод тогтвортой. LaBSE [`feng_2022_labse`] — хэл хоорондын өгүүлбэрийн embedding. GEMBA [`kocmi_2023_gemba`]
  — LLM-ээр QE (GPT-3.5-аас том загварт л ажилладаг гэж зохиогчид бичсэн).
- **Санаа (хоёр хувилбар):**
  (а) **Шууд cross-lingual оноо:** bge-m3 (`config/default.yaml: embedding_model`, аль хэдийн RAG-д ачаалагддаг) -аар
  cos(монгол эх, англи орчуулга). Нэмэлт загвар, үүсгэлтгүй.
  (б) **Round-trip:** M1/MADLAD-аар en→mn буцааж (M1 нь 322 en→mn мөрөөр сургагдсан), cos(эх, буцсан) ба chrF++(эх, буцсан).
  Оноог (1) n-best-ээс сонгоход (R1.3), (2) муу орчуулгыг bilingual fallback руу (R1.2), (3) abstain/clarify-ийн нэмэлт шинж
  (`pipeline/abstain.py`) болгон ашиглана.
- **Нотолгоо:** RTT-QE нь MT-ийн хүний үнэлгээтэй хамааралтай (Moon нар). Монгол хэлэнд bge-m3-ын cross-lingual чанар
  **хэмжигдээгүй (баталгаагүй)**; LaBSE-ийн хэлний жагсаалтыг шалгаагүй. LLM-QE (GEMBA) 7B-д найдвартай биш — манайд тохирохгүй.
- **Манай кодод:** `translate.py`-д `qe_score(src, en, embedder)`; `retrieval/retriever.get_retriever(cfg)`-ийн embedder-ийг
  дахин ашиглана. Dev дээр эхлээд **шалгах туршилт:** QE оноо ба M1a-ийн асуулт бүрийн зөв/буруу (dev) хоорондын AUROC. AUROC
  < 0.6 бол цааш үргэлжлүүлэхгүй.
- **Kaggle:** (а) CPU/GPU-д bge-m3 600 өгүүлбэр ≈1–2 мин; (б) буцаах орчуулга ≈10 мин. SQL run хэрэггүй (оношлогоо) эсвэл
  fallback-д ≈30 мин.
- **Хүлээгдэх ахиц:** шууд EX ахиц 0…+2 **(баталгаагүй)**; хариулах боломжгүй/эргэлзээтэй асуултыг илрүүлэхэд нэмэлт дохио.
  Хамгаалалтад «орчуулгын итгэлийг хэмждэг» гэж хэлэх боломж.

### R1.5. Олон орчуулгын чуулга (SQL түвшинд) — T9(б)-ийн нарийвчлал

- **Эх сурвалж:** Sherborne нар [`sherborne_2020_bootstrapping`] (олон MT-ийн гаралтыг paraphrase болгох); Ohmer нар
  [`ohmer_2023_form_meaning`] (хэл/хэлбэрийн олон «sense» дээрх self-consistency нь ойлголтын хэмжүүр); self-consistency
  [`wang_2023_self_consistency`].
- **Санаа:** RESEARCH_TECH_2 T9(б)-д бичсэн. Нэмэх зүйл: орчуулгын **эх үүсвэрийг олон янз** болгох нь нэг загварын n-best-ээс
  илүү бие даасан алдаа өгнө: (1) M1 n-best-ийн шилдэг 2 (R1.3), (2) Qwen3.5-9B.fix кэш (аль хэдийн байгаа, `build/translations/`),
  (3) латин асуултын хувьд «none» ба «improved» галиглалын хоёр зам. Санал хураалтад орчуулга бүрийн QE оноогоор (R1.4) жин өгнө.
- **Нотолгоо:** Манай чуулга p = 0.006 (test) — одоогийн 5 гишүүн нэг орчуулгатай. Qwen ба M1-ийн алдаа өөр төрлийн (Qwen —
  нэр томьёо 46.3%, утга 63.6%; M1 — нэр томьёо 69.0%, утга 13.6%) тул нэмэлт мэдээлэл өгөх магадлалтай **(баталгаагүй)**.
- **Манай кодод:** `reselect --extra` (кэш тус бүрээр run). Код өөрчлөлт бага. `I3t` run-ийн JSONL (Qwen орчуулгатай) dev-д
  аль хэдийн байвал **шинэ GPU-гүйгээр** M1ens-д нэмж туршина.
- **Kaggle:** Qwen орчуулгатай run байхгүй бол ≈2 цаг; M1 alt орчуулга ≈10 мин + run ≈2 цаг.
- **Хүлээгдэх ахиц:** +2…+6 (T9-ийн тооцоо, **баталгаагүй**). Нэгээс илүү SQL run шаардана — квотоор хязгаарлагдана.

### R1.6. Нэр томьёоны хязгаарлалт: hint → шалгалт → (сонголтоор) constrained decoding

- **Эх сурвалж:** Dinu нар [`dinu_2019_terminology`] — загварыг inline нэр томьёогоор сургах нь constrained decoding-оос үр
  дүнтэй, хурдан. Bergmanis & Pinnis [`bergmanis_2021_lemma_annotations`] — лемм (толь бичгийн хэлбэр)-ээр тэмдэглэх; морфологи
  баян хэлэнд нэр томьёоны нарийвчлал хүний үнэлгээгээр +47.7 хувь (латви). Hokamp & Liu [`hokamp_2017_gbs`], Post & Vilar
  [`post_2018_dba`] — decoding-ийн хатуу хязгаарлалт.
- **Санаа ба байдал:** M1 аль хэдийн Dinu/Bergmanis маягаар (`[T: монгол = англи]` hint-тэй) сургагдсан — энэ нь онолын хувьд зөв
  сонголт гэдгийг тайланд иш татаж болно. Үлдсэн алхам: hint-ийн англи нэр томьёо гаралтад байхгүй бол (R1.2-ын шалгалт 3) тэр
  асуултыг `force_words_ids`-тэй beam search-ээр дахин орчуулах.
- **Нотолгоо:** M1 нэр томьёо 69.0%, M1g8 (8 hint) +13/−14 — hint-ийг нэмэх нь ахиц өгөөгүй. Хатуу хязгаарлалт олон утгатай
  hint-ийг («A / B» хоёр хувилбар) буруу хүчээр оруулах эрсдэлтэй. transformers 5-д constrained beam search хэвээр байгаа эсэх
  **баталгаагүй** (4.x-ийн сүүлээр deprecated болсон гэж санаж байна).
- **Манай кодод:** `HFSeq2Seq._generate` (зөвхөн hint нь нэг англи хэлбэртэй үед). Эхлээд кэш дээр hint-ийг дагаагүй асуултын тоог
  тоолох.
- **Kaggle:** цөөн асуулт дахин орчуулах ≈2–5 мин.
- **Хүлээгдэх ахиц:** 0…+2 **(баталгаагүй)**. Тэргүүлэх биш.

### R1.7. Back-translation-оор MT-ийн сургалтын өгөгдөл нэмэх (M2)

- **Эх сурвалж:** Sennrich нар [`sennrich_2016_backtranslation`] — зорилтот хэлний нэг хэлт өгөгдлийг урвуу загвараар орчуулж
  сургалтад нэмэх.
- **Санаа:** Англи асуултын сан (BIRD/Spider-ийн асуулт биш — эрх ба домэйн; манай `knowledge/examples*.jsonl`-ийн англи
  тайлбар, `training/synth_own.py`-ийн англи загвар асуулт) → MADLAD en→mn → (монгол синтетик, англи жинхэнэ) хосоор M1-ийг
  нэмж сургах. Mn тал нь «машин», en тал нь жинхэнэ тул mn→en загварт тохиромжтой (Sennrich-ийн тохиргоо).
  Латин хувилбарыг `normalize.translit`-ээр үүсгэнэ.
- **Нотолгоо:** NMT-д сонгодог, байнга ахиц өгдөг арга. Манай M1 нь аль хэдийн 8 500 мөрөөр сургагдсан (зарим нь синтетик латин) —
  нэмэлт ахиц буурах хандлагатай **(баталгаагүй)**. Dev-тэй давхардлыг `training.yaml: dedup_threshold`-аар шүүх шаардлагатай.
- **Kaggle:** en→mn 3–5 мянган өгүүлбэр ≈1 цаг; M1 дахин сургах ≈3.5–4 цаг (V16: 270 алхам × 48 с) — 2 сесс. Өндөр зардал.
- **Хүлээгдэх ахиц:** chrF++ +1…+3, EX 0…+3 **(баталгаагүй)**. Хамгаалалтын өмнө тэргүүлэх биш.

### R1.8. Монгол хэлний морфологи ба нөөц

- **Олдсон нөөц:** MM-Eval [`zhang_2024_mm_eval`], MonCulture-Eval [`minggad_2026_monculture_eval`] (үнэлгээний сан, Text2SQL биш);
  CMiLBench **(баталгаагүй, хуудсыг нээгээгүй)**; MADLAD-400 [`kudugunta_2023_madlad`] (Apache-2.0, монгол багтсан).
  2024–2026 оны нээлттэй кирилл монгол морфологийн анализатор, NER сан хайлтаар **олдсонгүй** (хуучин ажлууд ихэнхдээ уламжлалт
  монгол бичгийн). NLLB-200 нь CC-BY-NC тул ашиглахгүй (`translate.py`-ийн docstring-д аль хэдийн дурдсан).
- **Манайд:** `translate_terms._stem` (урт үгэнд сүүлийн 3 үсгийг тэвчих) ба `normalize.strip_suffix` / `stem_variants` гэсэн
  хоёр өөр дүрэм зэрэг байна. CSpider/ViText2SQL-ийн сургамжаар үгийн хуваалт/морфологи нь холболтын чанарт нөлөөлнө.
  Санал: `term_hints`-ийг `normalize.stem_variants`-тэй нэгтгэх (нэг эх сурвалж), dev-ийн hint recall-ийг
  (`scripts/mt/term_accuracy.py`) хэмжиж харьцуулах. Шинэ нөөц татах шаардлагагүй.
- **Хүлээгдэх ахиц:** EX-д 0…+1 **(баталгаагүй)**; кодын цэвэр байдал, тайланд «монгол морфологийг хэрхэн шийдсэн» хэсэг.

## 4. Шилдэг 3 зөвлөмж

1. **R1.3 + R1.4(а) — n-best кэш ба QE оноо (нэг Kaggle сесс, ≈15 мин GPU + SQL run-гүй оношлогоо).**
   `HFSeq2Seq`-д `num_return_sequences=4`-тэй dev кэш үүсгэж, MBR-ээр сонгосон орчуулга, n-best-ийн санал нийлэлт, bge-m3
   cos(эх, орчуулга)-г хадгална. Эхлээд **dev дээр AUROC**: эдгээр оноо M1a-ийн буруу асуултыг ялгаж чадах уу? Энэ нь R1.2, R1.5-ийн
   аль алинд хэрэгтэй суурь бөгөөд «translate-test-ийн эрсдэлийг хэмжсэн» гэсэн хамгаалалтын нэмэлт аргумент.
2. **R1.2 — орчуулгын дараах тогтмол шалгалт → асуулт бүрт `bilingual` fallback.** CPU-д кэш дээр тооцно, зөвхөн
   шалгалтад унасан асуултыг дахин ажиллуулж reselect-ээр нийлүүлнэ. Эрсдэл бага (давсан асуулт хэвээр), M1-ийн
   13.6%-ийн утга хадгалалт ба тоо алдагдлыг барина.
3. **R1.5 — олон эх үүсвэрийн орчуулгын чуулга (M1 + Qwen.fix + MBR alt).** Qwen орчуулгатай dev run (I3t) аль хэдийн байвал
   GPU-гүйгээр M1ens-д `--extra`-аар нэмж туршина; QE оноогоор жинлэнэ. Одоогийн чуулгын бүх гишүүн нэг орчуулгатай байгаа
   хязгаарлалтыг арилгана.

R1.1 (тоо/огноо) нь R1.2-ын шалгалт тоо алдсан асуултыг олон олбол л хийх нь зүйтэй. R1.7 (back-translation, M2) нь
хамгаалалтын дараах ажил.
