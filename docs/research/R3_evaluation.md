# R3. Үнэлгээний аргачлалын нягт байдал (хамгаалалтад бэлтгэх) — 2026-10-30

Хамрах хүрээ: EX ба түүний худал эерэг/сөрөг, test-suite accuracy, BIRD/Spider 2.0-ийн хэмжүүр, хариулах боломжгүй ба
хоёрдмол асуултын үнэлгээ, жижиг test дээрх статистик, test-д хэт тааруулах эрсдэл, хүний үнэлгээ. Мөн `src/mn_text2sql/eval/`
кодын аудит. Зөвхөн судалгаа ба санал: код, тохиргоо, дипломын текстэд өөрчлөлт оруулаагүй.

Тэмдэглэгээ: «баталгаагүй» = эх сурвалжийг энэ удаад шууд нээж шалгаагүй, санах ойгоос эсвэл хоёрдогч эх сурвалжаас авсан тоо.
Ахиц ба зөрүүг «хувь» гэж бичив (процентийн нэгж).

## 1. Гол дүгнэлт (товч)

1. **EX-ийн хэрэгжилт ерөнхийдөө зөв, уян хатан.** Баганын дарааллыг харгалзахгүй, мөрийг multiset-ээр (давхардлын тоог
   хадгалж) харьцуулдаг, тоонд хүлцэлтэй, order_matters-ийг асуулт бүрт гараар тэмдэглэсэн. Энэ нь Spider/BIRD-ийн албан
   ёсны скриптээс (BIRD: `set(pred) == set(gold)` — давхардлыг үл тоодог) илүү хатуу ба шударга.
2. **Хамгийн том арга зүйн цоорхой — эцсийн системүүдэд TS-EX тооцоогүй.** Test-suite (8 хуулбар DB) бэлэн боловч TS-EX
   зөвхөн C1–D2 (dev) дээр байна. D2: EX 16.52% → TS-EX 15.62% (37 зөвийн 2 нь санамсаргүй таарсан). M1a/M1ens-ийн
   test дээр TS-EX байхгүй.
3. **«Нийт EX» нь гурван өөр даалгаврыг хольдог.** Хоёрдмол асуултад тодруулга асуувал, хариулах боломжгүй асуултад
   ямар ч шалтгаанаар (алдаа ч гэсэн) хариулахгүй бол «зөв» гэж тооцдог. Бүгдэд нь тодруулга асуудаг тэнэг систем test
   дээр 49/200 = **24.5%** «нийт EX» авна — энэ нь D2-ийн 21.0%-иас өндөр. Тиймээс нийт EX-ийг үндсэн хэмжүүр болгох нь
   эрсдэлтэй; хариулах боломжтой EX + TrustSQL оноо + татгалзалтын precision/recall гэж салгах хэрэгтэй.
4. **Олон харьцуулалт.** Ch6-д ~16 McNemar p-утга бий. Бүгдийг нэг гэр бүл гэж Holm-оор засвал dev I3t→M1a
   (p = 0.0054), dev M1a→M1ens (p = 0.0063), test I3t→M1a (p ≈ 0.007) нь засварласан p ≈ 0.054–0.057 болж 0.05-ийг
   давна. **Dev ба test-ийг тусдаа гэр бүл** гэж тодорхойлбол (dev = хайгуулын, test = баталгаажуулах) §4.3-ын тооцоо
   хүчинтэй гарсан ч **бүх гол дүгнэлт Holm-ын дараа хүчинтэй гэж хэлэх боломжгүй** (2026-10-31 засвар,
   `docs/review/FULL_REVIEW_2026-10-30.md` §2): test D2→H4-ийн хариулах боломжтой ахиц +26/−15, p = 0.117 (нийт p = 8.6e-4
   нь голдуу татгалзал, тодруулгаас); test I3t→M1a нь test-ээс мэдээлэл авсан 13 асуултгүйгээр p = 0.047 — Holm-ыг давахгүй
   (загвар төстэй 6-г ч хасвал p = 0.16). Үүнийг урьдчилан тунхаглах хэрэгтэй.
5. **Test жижиг: McNemar-ийн мэдрэх чадвар.** 151 хариулах асуулт дээр 30 зөрүүтэй хос байхад ач холбогдолтой гэж
   батлахад цэвэр ахиц ≥ +12 асуулт (**≈ 7.9 хувь**) хэрэгтэй. Иймд 2–5 хувийн ахицыг test дээр батлах боломжгүй — «ялгаагүй»
   гэж бус «мэдрэх чадвар хүрэлцээгүй» гэж бичих нь зөв.
6. **Gold-ын чанарыг хүн шалгаагүй.** BIRD Mini-Dev-ийн 52.8%, Spider 2.0-Snow-ийн 62.8% жишээнд тэмдэглэгээний алдаа
   илэрсэн (Jin et al., 2026). Манай gold LLM agent-уудын бичсэн тул 50 асуултын хүний аудит (Cohen's κ) хамгийн их
   үнэ цэнэтэй нэмэлт.

## 2. Судалгааны үр дүн (уран зохиолын тойм)

### 2.1 EX, EM ба test-suite accuracy
- **EM (exact set match)** — SQL-ийн бүтцийг харьцуулна; зөв боловч өөрөөр бичсэн SQL-ийг буруу гэдэг (худал сөрөг их).
- **EX (execution accuracy)** — нэг DB дээрх үр дүнг харьцуулна. Худал эерэг: буруу SQL тухайн өгөгдөл дээр санамсаргүй
  ижил үр дүн гаргах (жишээ нь `WHERE status='A'` ба шүүлтгүй SQL хоёр хоосон биш ч ижил тоо өгөх).
- **Test-suite accuracy (Zhong, Yu, Klein, 2020)** — gold-ын «ялгах чадвар» өндөр олон DB хуулбар (fuzzing + distillation)
  дээр бүгдэд нь таарвал зөв. Тэд Spider дээр EX-ийн худал эерэгийг мэдэгдэхүйц бууруулсан (тодорхой хувь — баталгаагүй).
  Манай `testsuite.py` нь энэ санааны хялбар хувилбар: 8 DB, гараар сонгосон хувилбар (NULL, тэнцүү утга, DPD/огнооны хил,
  хоосон хүснэгт). Zhong-ийн аргатай ялгаа: манайх gold-ыг мутацлах замаар хуулбарыг «distill» хийдэггүй, тиймээс аль
  хуулбар нь хэр ялгадгийг хэмжээгүй.
- **Pourreza & Rafiei (2023)** — Spider-ийн EX-ийн «худал сөрөг»-ийг хүнээр шалгаж, загваруудын бодит нарийвчлал EX-ээс
  өндөр болохыг харуулсан (тоо — баталгаагүй). Гол шалтгаан: олон зөв тайлбар, нэмэлт багана, эрэмбэ, gold-ын алдаа.

### 2.2 BIRD-ийн хэмжүүр
- **EX**: албан ёсны скрипт `set(predicted_res) == set(ground_truth_res)` — мөрийн дараалал, **давхардал** хоёуланг
  үл тоодог; багана байрлалаараа (tuple) харьцуулагдана (баганын дараалал чухал).
- **VES / R-VES**: зөвхөн EX-ээр зөв асуулт дээр gold ба таамгийн гүйцэтгэлийн хугацааны харьцааг шагнал болгоно.
  R-VES (mini-dev, 2024) нь харьцааг шат дараатай шагнал (жишээ нь ≥2 → 1.25, 1–2 → 1.0, … ) болгож дуу чимээг багасгасан
  (шатлалын яг утга — баталгаагүй). Манай ажилд хугацааг p50/p95-аар тайлагнасан нь бүтээгдэхүүний хувьд илүү ойлгомжтой;
  VES-ийг нэмэх нь заавал биш.
- **Soft-F1** (BIRD mini-dev): мөр бүрийг утгын олонлогоор тааруулж хэсэгчилсэн оноо өгнө; баганын дараалал ба
  нэмэлт/дутуу баганад зөөлөн. Манай `compare.soft_f1` үүнийг хэрэгжүүлсэн бөгөөд «ойр алдаа» шинжилгээнд ашиглагдсан.
- BIRD-ийн өгөгдлийн чанар: Wretblad et al. (2024) BIRD-ийн санхүүгийн домэйнд асуулт/gold-ын алдаа их байгааг харуулсан;
  Jin et al. (2026, PVLDB) BIRD Mini-Dev-ийн 52.8%, Spider 2.0-Snow-ийн 62.8% жишээнд тэмдэглэгээний алдаа олж, засварласан
  дэд олонлог дээр leaderboard-ийн байр −9…+9 байраар өөрчлөгдсөнийг харуулсан.

### 2.3 Spider 2.0 (Lei et al., ICLR 2025)
- EX-ийн **баганын дэд олонлогийн тааралт**: gold-ын багана бүр таамгийн үр дүнд (агуулгаараа, байрлалаас үл хамааран)
  байвал зөв; **нэмэлт багана зөвшөөрнө**. Тоонд ~0.01 хүлцэл. Мөрийн дарааллыг зөвхөн шаардлагатай үед шалгана
  (`ignore_order` тугтай — нарийвчилсан дүрэм баталгаагүй). Учир: бодит ажлын асуултын «гаралтын багана» ихэвчлэн
  тодорхой бус байдаг.
- Манай хатуу дүрэм (баганын тоо яг ижил) нь Spider 2.0-оос хатуу. Иймд «нэмэлт багана»-аас үүдэх худал сөрөгийг
  тусад нь хэмжих нь зүйтэй (§5, Хүснэгт A).

### 2.4 EX-ийн худал эерэг ба худал сөрөгийн эх үүсвэр
| Эх үүсвэр | Төрөл | Манай код |
|---|---|---|
| Мөрийн дараалал | ORDER BY шаардсан асуултад дарааллыг үл тоовол худал эерэг; шаардаагүйд дарааллыг тооцвол худал сөрөг | `order_matters` гараар (test: 14/151) — зөв |
| Давхардал | `set()` нь давхардлыг арилгаж худал эерэг үүсгэнэ (BIRD) | multiset (`Counter`) — зөв |
| Баганын дараалал | байрлалаар харьцуулбал худал сөрөг | зохицлыг хайдаг (≤7 багана) — зөв, гэхдээ §3 A4 |
| Нэмэлт/дутуу багана | id-г нэмэлтээр гаргавал худал сөрөг | хатуу (ижил тоо) — §3 A3 |
| Float бөөрөнхийлөлт | ROUND(x,1) vs бөөрөнхийлөөгүй | abs 0.01 / rel 1e-6 — §3 A1 |
| Хувь vs бутархай (53.2 vs 0.532) | худал сөрөг (эсвэл зөв сөрөг — тодорхойлолтоос хамаарна) | хатуу |
| Код vs нэр, огнооны дүрслэл | худал сөрөг | `value_maps`, `PERIOD_TRANSFORMS` — уян |
| LIMIT + тэнцүү утга (ties) | gold-ын сонгосон мөр тодорхой бус → худал сөрөг | шийдээгүй (test: LIMIT-тэй 13, order_matters-гүй 2) |
| Хоёулаа хоосон | дурын хоосон таамаг таарна → худал эерэг | `True` (BIRD-тэй ижил), gold хоосон байхгүй гэж шалгасан |
| Санамсаргүй ижил тоо | худал эерэг | test-suite-ээр л илэрнэ |

### 2.5 Хариулах боломжгүй ба хоёрдмол асуултын үнэлгээ
- **TrustSQL (Lee et al., 2024)** — Reliability Score: зөв хариулт/зөв татгалзал +1, хариулах боломжтойгоос татгалзсан 0,
  буруу хариулт эсвэл боломжгүй асуултад хариулсан −c (c = 1, 10, N). Манай `trust_score` үүнийг хэрэгжүүлсэн (c = 1, 5, 10)
  ба хоёрдмол асуултыг өөрсдөө өргөтгөсөн. **Ch6-д TrustSQL оноо огт тайлагнагдаагүй** — бэлэн тоог нэмэх нь хялбар.
- **AmbiQT (Bhaskar et al., 2023)** — хоёрдмол асуулт бүрд 2 зөв SQL; загвар top-k-д **хоёуланг** нь гаргасан эсэхийг хэмждэг.
- **AMBROSIA (Saparina & Lapata, NeurIPS 2024)** — scope, attachment, vagueness; бүх тайлбарыг олсон эсэх (AllFound маягийн),
  тайлбар тус бүрийн recall/precision (хэмжүүрийн нэр — баталгаагүй). Загварууд ихэвчлэн зөвхөн нэг тайлбарыг олдог.
- **PRACTIQ (Dong et al., NAACL 2025)** — 4 хоёрдмол + 4 хариулах боломжгүй ангилал, 2 800 харилцан яриа; (1) асуултын
  ангиллыг таних, (2) тодруулгын дараах SQL гэсэн хоёр дэд даалгавар.
- **Selective prediction / coverage–risk** (El-Yaniv & Wiener, 2010; Geifman et al., 2019): итгэлийн босгоор хамралт
  (coverage) ба эрсдэл (1 − selective accuracy)-ийн муруй, түүний доорх талбай **AURC** (бага нь сайн). Манай
  `abstention_curve` муруйг гаргадаг боловч AURC тооцдоггүй.
- **Манай хэрэгжүүлэлтийн онцлог:** хоёрдмол асуултад «аль нэг тайлбартай таарвал зөв» (`runner.py:217-220`, `dataset.py:52-56`).
  Энэ нь AmbiQT/AMBROSIA-аас зөөлөн (тэд бүх тайлбарыг шаарддаг). Хамгаалалтад үүнийг ил тод хэлэх хэрэгтэй.

### 2.6 Жижиг test дээрх статистик
- **McNemar exact** (McNemar, 1947) — хос асуулт, зөвхөн зөрүүтэй хосыг (b, c) ашиглана; манай сонголт зөв (Dror et al.,
  2018-ын зөвлөмжтэй нийцнэ).
- **Нэг пропорцийн CI** — Wilson (1927) жижиг n-д Wald-аас найдвартай. **Ялгаварын CI** — хос өгөгдөлд Newcombe (1998)-ийн
  хос арга эсвэл хос bootstrap (асуултаар дахин түүвэрлэж ΔEX тооцох).
- **Мэдрэх чадвар** — Card et al. (2020): NLP-ийн олон test set нь жижиг ахицыг илрүүлэх чадваргүй; «ач холбогдолгүй» ≠ «нөлөөгүй».
- **Олон харьцуулалт** — Holm (1979) step-down нь Bonferroni-оос хүчтэй, таамаглал шаардахгүй. Гэр бүлийг урьдчилан тодорхойлно.
- **Test-ийг дахин ашиглах** — Dwork et al. (2015): test-ийн хариу харж олон удаа сонголт хийх нь адаптив overfitting
  үүсгэнэ. GPU-гүй `reselect` нь test дээр хэдэн ч тохиргоог секундэд ажиллуулах боломж олгодог тул энэ эрсдэл манайд бодит.

### 2.7 Хүний үнэлгээ
- Gold-ын аудит (Jin et al., 2026-ийн протокол): асуулт ↔ gold SQL ↔ үр дүнг хоёр шинжээч бие даан шалгаж, санал зөрвөл
  гуравдагч шийднэ; алдааны ангилал (асуулт хоёрдмол, gold буруу, мэдлэг дутуу г.м.), Cohen's κ.
- EX-ийн шийдвэрийн аудит (Pourreza & Rafiei, 2023 маягийн): EX-ээр «зөв»-ийн түүвэрт худал эерэг, «буруу»-гийн түүвэрт
  худал сөрөг хэд байгааг хүнээр тоолж, EX-ийн хазайлтыг (bias) тооцоолох.
- LLM judge (`eval/judge.py`) нь κ ≥ 0.6 орчим хүний шошготой тохирсон үед л туслах хэмжүүр болно (код аль хэдийн
  `judge-validate`-тэй).

## 5. Ch6-д нэмэх хэмжүүр ба хүснэгт (санал)

**Хүснэгт A. EX-ийн хувилбарууд (test, эцсийн 2–3 тохиргоо).** Багана: EX-strict (`ex_strict`, уян дүрэмгүй) / EX (одоогийн) /
EX-subset (нэмэлт багана зөвшөөрсөн) / **TS-EX** / Soft-F1. Зорилго: EX-ийн уян дүрэм хэдэн асуултыг «аварсан», test-suite
хэдийг «унагасан»-ыг харуулах. Хэрэв TS-EX тооцох боломжгүй бол D2-ийн dev тоог (16.5 → 15.6) жишээ болгож оруулах.

**Хүснэгт B. Найдвартай байдал (test, ангиллаар).**
| Тохиргоо | Хариулах EX | Хамралт (coverage) | Selective acc. | Over-refuse/clarify (хариулах дээр) | Боломжгүй: зориуд refuse | Хоёрдмол: clarify / тайлбар таарсан | TrustSQL c=1 / c=10 |
Мөр болгон: D2, H4, E2, E3c, M1a (+ M1ens/M1ensr хэмжигдвэл), мөн **«бүгдэд clarify» trivial baseline** (24.5% нийт).
Бүх тоо `summarize()`-д бэлэн (`coverage_pct`, `selective_accuracy`, `trust`, `unanswerable_detected_pct`, `ambiguous`).

**Хүснэгт C. McNemar өргөтгөсөн.** Багана: b / c / ΔEX (хувь) / ΔEX-ийн 95% CI (хос bootstrap эсвэл Newcombe) / p / Holm адж. p /
гэр бүл (dev/test). Энэ нь «ач холбогдолтой ч ахиц хэр том вэ» гэдэгт хариулна.

**Зураг D. Coverage–risk муруй + AURC** (M1a ба M1ens, хариулах боломжтой асуулт, итгэл = санал нэгдлийн хувь). E3c-ийн
0.5 босгыг муруй дээр тэмдэглэх.

**Хүснэгт E. Хүний аудит (§6).** Gold-ын алдааны хувь (Wilson CI), EX-ийн худал эерэг/сөрөгийн хувь, κ.

**Текстэд:** (1) CI-ийн арга (Wilson) ба McNemar-ийн exact хувилбарыг арга зүйн хэсэгт; (2) «Test-ийг хэдэн удаа, ямар
тохиргоогоор ажиллуулсан» бүрэн жагсаалт (test-ийн хандалтын бүртгэл) — сонгомол тайлагналгүйг харуулна; (3) нэг seed, нэг
ажиллуулалт гэдгийг хязгаарлалтад; (4) хоёрдмол асуултын «аль нэг тайлбар» дүрмийг ил тод.

## 7. Шалгагчийн байж болох асуулт ба хариулт

**А1. «EX 50.5% гэдэг нь бодит нарийвчлал мөн үү? Буруу SQL санамсаргүй зөв үр дүн гаргаагүй гэж яаж мэдэх вэ?»**
— Тийм эрсдэл байгаа учраас Zhong et al. (2020)-ийн test-suite санааг хэрэгжүүлж 8 өөрчилсөн хуулбар DB (NULL, тэнцүү утга,
огнооны хил, хоосон хүснэгт) үүсгэсэн. D2 дээр EX 16.5% → TS-EX 15.6% буюу зөвийн ~5% нь санамсаргүй таарсан байв.
[Хэрэв хийгдвэл: эцсийн M1a-д TS-EX = … ] Мөн хүний аудитаар 25 «зөв»-ийн … нь худал эерэг байв.

**А2. «Нийт EX-д хариулах боломжгүй асуултаас татгалзсан нь зөв гэж тоологдож байна. Систем бүгдээс татгалзвал яах вэ?»**
— Тийм учраас үндсэн хэмжүүр бол хариулах боломжтой асуултын EX (53.6%). Нийт EX-ийн доод суурь (бүгдэд тодруулга) 24.5%.
Найдвартай байдлыг TrustSQL онооны (буруу хариултыг −c-ээр торгодог) ба хариулах боломжтой асуултаас хэт татгалзсан хувиар
тусад нь үнэлсэн (Хүснэгт B).

**А3. «200 асуулт хэтэрхий цөөн биш үү?»**
— Нэг пропорцийн 95% CI ±7 хувь (хариулах 151 дээр ±8 хувь). Тиймээс бүрэлдэхүүн бүрийн нөлөөг хос асуулт дээрх McNemar
тестээр (асуулт хоорондын хэлбэлзлийг хасдаг) шалгасан; ~8 хувиас бага ахицыг test-ээр батлах чадваргүй гэдгийг хүлээн
зөвшөөрч, ийм ахицыг «батлагдаагүй» гэж бичсэн. Spider/BIRD-ийн dev ч 1 000–1 500 асуулттай; манай 500 асуулт нэг домэйнд гүн.

**А4. «Та олон тохиргоо туршсан. Олон харьцуулалтын засвар хийсэн үү?»**
— Dev-ийг хайгуулын, test-ийг баталгаажуулах гэр бүл гэж тодорхойлсон. Test-ийн 6 харьцуулалтад Holm засвар хийхэд
(H4→E2 нийтээс бусад) бүгд p < 0.05 хэвээр. Бүх 16 харьцуулалтыг нэг гэр бүл гэвэл M1a ба M1ens-ийн ахиц засварласан
p ≈ 0.055 болж хил дээр гардаг — үүнийг хязгаарлалтад бичсэн.

**А5. «Test-ийг харж тохиргоо сонгоогүй гэдгийг яаж батлах вэ?»**
— Дүрэм, босго, abstain-ийн жин бүгд dev-ээс (family CV-ээр) гаргагдсан; `adaptive.py` dev-ийг л уншдаг; pick-ийг test-д
асаах шийдвэр dev-ийн McNemar дээр автомат (`PICK_TEST`). Test-ийг ажиллуулсан бүх тохиргоог (сонгомол биш) Хүснэгт~tab:test-д
жагсаасан. Гэвч GPU-гүй reselect test дээр хямд тул адаптив overfitting-ийн эрсдэл үлдэнэ гэдгийг хүлээн зөвшөөрнө.

**А6. «Gold SQL-ийг LLM бичсэн. Gold буруу байвал?»**
— Gold бүрийг DB дээр гүйцэтгэж (check-gold), test-suite хуулбар бүр дээр алдаагүй ажиллахыг шалгасан, өөр agent сохроор
хянасан. Гэхдээ BIRD Mini-Dev-ийн 52.8% нь тэмдэглэгээний алдаатай байсан (Jin et al., 2026) тул [хийгдвэл] 50 асуултын
хүний аудит хийж алдааны хувь …%, κ = … гарсан.

**А7. «Баганын дараалал, мөрийн дараалал, давхардлыг яаж шийдсэн? BIRD-тэй ижил үү?»**
— BIRD нь `set()` ашиглаж давхардлыг үл тоодог; манайх multiset (давхардлыг тоолно) тул илүү хатуу. Баганын дарааллыг
харгалзахгүй (зохицлыг хайна). Мөрийн дарааллыг зөвхөн асуулт ORDER шаардсан (test-д 14) үед шалгана. Тоонд abs 0.01 /
rel 1e-6 хүлцэл. Нэмэлт багана буруу гэж тооцогдоно (Spider 2.0-оос хатуу).

**А8. «Хоёрдмол асуултыг аль нэг тайлбартай таарвал зөв гэдэг нь хэт зөөлөн биш үү?»**
— Тийм, AMBROSIA/AmbiQT бүх тайлбарыг шаарддаг. Бодит хэрэглээнд систем нэг тайлбарыг сонгоод түүнийгээ ил харуулдаг
(ашигласан хүснэгт ба SQL) учир «аль нэг» дүрмийг сонгосон. Тодруулга асуусан болон тайлбартай таарсныг тусад нь тайлагнасан.

**А9. «Үр дүн давтагдах уу? Seed хэд вэ?»**
— Бүх run нэг seed (s0); run бүр `eval_set` sha1, DB fingerprint, prompt хувилбар, кодын commit-ийг бичлэг бүрт хадгалдаг
(`runner.py:281-284`). Seed-ийн хэлбэлзлийг GPU төсвийн улмаас хэмжээгүй — хязгаарлалт. (8 хувилбарын санал хураалт
нь нэг үүсгэлтийн хэлбэлзлийг бууруулдаг.)

**А10. «Яагаад BIRD-ийн VES-ийг тайлагнаагүй вэ?»**
— VES нь gold-оос хурдан SQL-ийг шагнадаг; манай синтетик DB жижиг (~650 мянган мөр) тул гүйцэтгэлийн хугацааны ялгаа
мс-ийн түвшинд, хэмжилтийн дуу чимээнээс бага. Хэрэглэгчид хамааралтай нь асуултын бүрэн хугацаа (p50/p95) тул түүнийг
тайлагнасан.

**А11. «Dev ба test-ийн хооронд мэдээлэл алдагдсан уу (leakage)?»**
— Family-аар хуваасан, давхцал 0 (`split.py`). Орчуулагчийн 8 500 сургалтын өгүүлбэр dev-тэй яг давхцаагүйг шалгасан;
[санал: test-тэй ойролцоо давхцлыг (chrF > 80) мөн шалгах].
