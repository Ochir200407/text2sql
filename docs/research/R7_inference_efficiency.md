*Огноо: 2026-10-30. Хамрах хүрээ: зөвхөн судалгаа ба санал. Код, тохиргоо, скрипт өөрчлөөгүй.*

## 0. Товч дүгнэлт

1. **Гол зардал нь prefill.** Dev H4 (300 асуулт, 1 хувилбар): prompt-ийн медиан **20 060 токен** (p5 19 536, p95 20 478),
   нийт prefill **5.76 сая** токен. Харин completion нийт **0.25 сая** токен. T4 (sm75, FlashAttention-2 байхгүй) дээр
   20k токены prefill л гэхэд асуулт тутамд хэдэн секунд зарцуулна.
2. **Decode-ийн 63% нь «гогцоо» (loop)-д үрэгдэж байна.** Greedy H4 дээр 52/300 (17%) гаргалт `max_tokens = 3072`-д яг
   тулж тасарсан. Тэдгээр нь нийт completion токены 160k/253k-ийг эзэлнэ. Тасраагүй гаргалтын хамгийн урт нь бараг үргэлж
   ≤ 1 000 токен (тасраагүй 248-аас зөвхөн 2 нь 2.8–3.0k). Тасарсан гаргалтын зөв хувь 29% (15/52), богино гаргалтынх 39% (95/246).
3. **E2 (n = 8) T4 дээр KV-cache-ээр хязгаарлагддаг (тооцоо, баталгаагүй).** Qwen2.5-7B-ийн KV ≈ 56 KB/токен
   (28 давхарга × 4 KV head × 128 × 2 × fp16). TP = 2, `--gpu-memory-utilization 0.90` үед KV-д ойролцоогоор
   150–200k токен багтана. Энэ нь 23k токены ~7–8 дараалал юм. `workers = 8` × `n = 8` = 64 дарааллыг
   prefix caching л аварна: 8 түүвэр 20k prompt-ийн блокоо хуваалцана. Prefix caching ажиллахгүй бол preemption болж
   дахин тооцоолно. Энэ нь «T4 дээр E2 ~175 с/асуулт» (WORKLOG:183, 311)-ийн хамгийн магадлалтай тайлбар.
4. **T4 override `--enable-prefix-caching`-ийг хасдаг.** `scripts/notebook/make_notebook.py:126` (`notebooks/t2s_eval.ipynb`-д
   мөн адил) нь `models.yaml`-ийн `vllm_args`-ийг **бүтнээр** орлуулдаг (`serve_model.sh:42-44`). Үүний `base` мөрөнд
   prefix caching алга. vLLM V1-д энэ нь анхдагчаар асаалттай гэж баримт бичигт заасан тул бодит нөлөө Kaggle дээр суусан
   vLLM-ийн хувилбараас хамаарна (баталгаагүй). vLLM-ийн лог дахь `enable_prefix_caching=` ба «Prefix cache hit rate»-ээр
   шалгах шаардлагатай.
5. **Reproducibility-ийн цоорхой.** `eval/runner.py:435` нь meta-д `mspec.get("vllm_args")` буюу `models.yaml`-ийн bf16
   мөрийг бичдэг. T4 дээр бодит `T2S_VLLM_ARGS` (fp16, TP2)-ийг бичдэггүй. Жишээ нь dev H4/E2-ийн meta-д
   `--dtype bfloat16 ... --enable-prefix-caching` гэж байгаа нь A100 дээр ажилласан тул зөв. Харин T4-ийн run-уудад
   буруу утга бичигдэнэ. Мөн `options_hash` (`runner.py:289-293`) нь `vllm_args` ба `max_tokens`-ийг (`orchestrator.py:181`,
   `models.yaml`-аас) **агуулдаггүй**. Тиймээс эдгээрийг өөрчлөөд resume хийвэл хоёр өөр тохиргооны мөр нэг файлд
   холилдох эрсдэлтэй.

Дүгнэлт: T4 дээр хамгийн их хэмнэлтийг (а) гогцоо/урт reasoning-ийг таслах, (б) ижил хүсэлтийг run хооронд дахин үүсгэхгүй
байх (кэш), (в) prefix caching-ийг баталгаажуулж, `workers`-ийг KV-ийн багтаамжид тааруулах нь өгнө. Харин quantization
болон speculative decoding нь энэ prefill-д дарагдсан ачаалалд бага нөлөөтэй бөгөөд эрсдэл ихтэй.

## 2. Арга тус бүр: тохиргоо, хурдасгалт, эрсдэл

Хурдасгалтыг «одоогийн T4-ийн dev run-ын бүх хугацаатай харьцуулсан хэмнэлт» байдлаар өгөв. Бүх тоо **баталгаагүй**
(T4 дээр хэмжээгүй), харин §1-ийн токен статистик дээр тулгуурласан тооцоо юм.

### 2.1 Prefix caching (APC)

* **Механизм.** vLLM нь KV блокийг hash-аар хадгалж, ижил угтвартай хүсэлтэд prefill-ийг алгасдаг (Kwon et al., 2023;
  SGLang-ийн RadixAttention-ий санаатай адил, Zheng et al., 2024). Бидэнд гурван түвшинд хэрэгтэй:
  (1) `n = 8` түүвэр нэг prompt-ийг хуваалцана (vLLM `n` дотор ч гэсэн); (2) засварын хүсэлт (`orchestrator.py:534-539`) өмнөх яриаг
  бүтнээр нь дахин илгээдэг тул 20k угтвар нь давтагдана; (3) асуулт хооронд: prompt-ийн урт бараг тогтмол (19.5–20.5k),
  schema-ийн хэсэг (budget 13 000) ихэнхдээ ижил хүснэгтүүдээс бүрдэх тул **хүснэгтийн дараалал тогтмол бол** урт угтвар
  хуваалцагдана.
* **Тохиргоо.** `make_notebook.py:126`-ийн `base`-д `--enable-prefix-caching` нэмэх (V1-д анхдагч ч гэсэн тодорхой бичих нь
  хувилбараас хамаарахгүй болгоно). Шалгах арга нь vLLM-ийн лог дахь `Prefix cache hit rate` юм.
* **Хурдасгалт.** (1)–(2)-ын хувьд аль хэдийн асаалттай байж магадгүй. Асаалтгүй байсан бол E2-т **1.5–3 дахин** хурдасна
  (баталгаагүй). (3)-ын хувьд hit rate 40–60% бол prefill ~40% буурч, нэг үүсгэлттэй run **15–30%** хурдасна (баталгаагүй).
* **Нарийвчлал.** Онолын хувьд нөлөөгүй. Гэхдээ fp16-д кэштэй/кэшгүй prefill-ийн тооцооны дараалал өөр тул greedy гаргалт
  цөөн асуултад зөрж болно.
* **Reproducibility.** Бага эрсдэлтэй. Meta-д бодит аргументыг бичих хэрэгтэй (§3).

### 2.2 Chunked prefill ба `--max-num-batched-tokens`

* V1-д chunked prefill анхдагчаар асаалттай (vLLM V1 guide). Манай prompt 20k токен тул анхдагч жижиг chunk (2048 гэх мэт,
  хувилбараас хамаарна) нь нэг prompt-ийг ~10 алхамд хуваана. `--max-num-batched-tokens 8192` болгох нь GEMM-ийн
  үр ашгийг нэмж, prefill-д дарагдсан ачаалалд **5–15%** хэмнэнэ (баталгаагүй). Гэхдээ activation санах ой нэмэгдэж, KV-ийн
  багтаамж бага зэрэг багасна.
* Нарийвчлалд нөлөөгүй (fp16-ийн тоон зөрүүг эс тооцвол). Эрсдэл бага.

### 2.3 `--gpu-memory-utilization`, `--max-model-len`, `--max-num-seqs`, `workers`

* **KV-ийн багтаамж нь T4-ийн гол хязгаар** (§0.3). 0.90 → 0.95 болгоход GPU тус бүрт ~0.8 GB нэмэгдэж, KV ~+15–20%
  (≈ +30k токен) өснө. Эрсдэл нь eval явцад BGE-M3 (`knowledge/semantic.py`, `cached_model`) GPU 0-д ачаалагдвал OOM
  гарах явдал. Тиймээс eval үед embedder-ийг CPU-д ажиллуулах (`T2S_EMBED_DEVICE`) эсвэл 0.93-аар хязгаарлах хэрэгтэй.
* `--max-model-len 32768` (T4) ба 24576 (L4): V1 нь KV-ийг урьдчилан нөөцлөхгүй тул хурдад бараг нөлөөгүй. Харин L4-ийн
  тохиргоотой **ижил** байлгах нь (24576) reproducibility-д зөв. Засварын урт яриа хэтэрвэл `client.py:79-84` `max_tokens`-ийг
  автоматаар багасгадаг.
* **`workers`-ийг KV-д тааруулах.** vLLM-ийн лог дахь «GPU KV cache size: N tokens» ба «Maximum concurrency» мөрийг уншиж,
  greedy run-д `WORKERS ≈ N / 23 000` (≈ 6–8), E2-т `WORKERS ≈ N / (20 000 + 8 × 1 000)` (≈ 5–6) болгоно.
  Хэт олон зэрэг хүсэлт preemption/recompute үүсгэж, нийт throughput-ийг бууруулдаг. `--max-num-seqs`-ийг
  (V1-ийн анхдагч нь хэдэн зуу) 64 гэх мэтээр хязгаарлах нь CUDA graph-ийн санах ойг багасгана. **10–30%** (баталгаагүй).
  Эрсдэл: `workers` нь `options_hash`-д ордоггүй. fp16-д batch-ийн бүрэлдэхүүн өөрчлөгдөхөд greedy гаргалт бага зэрэг зөрж
  болно (vLLM нь анхдагчаар batch-invariant биш).

### 2.4 `--enforce-eager`

* CUDA graph нь жижиг batch-ийн decode-ийг хурдасгадаг ч GPU тус бүрт ~0.5–1 GB эзэлдэг. Манай eval prefill-д дарагдсан,
  KV-ээр хязгаарлагдсан тул eager горимд чөлөөлөгдсөн санах ой KV-д очно. Ингэснээр E2-т ашигтай байж болох ч greedy-д
  decode удааширна. Хүлээгдэх нөлөө нь **−10%-аас +10%** (баталгаагүй, хэмжихгүйгээр бүү өөрчил). Эхлүүлэх хугацаа
  ~1–2 минутаар богиносно (graph capture хийхгүй).

### 2.5 Tensor-parallel 2 ба хоёр replica

* fp16 7B-ийн жин ≈ 15.2 GB тул нэг T4 (16 GB)-д багтахгүй. **TP = 2 нь fp16-д цорын ганц сонголт** юм
  (`make_notebook.py:124` үүнийг шалгадаг). Kaggle-ийн 2×T4 нь NVLink-гүй, PCIe-ээр холбогддог тул давхарга бүрийн all-reduce
  нэмэлт зардал гаргана.
* Хоёр replica (GPU тус бүрт нэг vLLM, `--port 8000/8001`, клиент талд round-robin) хийх боломж нь зөвхөн int4/int8
  жинтэй үед гарна (§2.7). Энэ нь **1.3–1.8 дахин** throughput өгч болох ч (баталгаагүй) загварын жин өөрчлөгдөнө.
  Одоогийн `client.py` нь нэг `base_url`-тэй тул клиентийн өөрчлөлт шаардлагатай.

### 2.6 LoRA-ийн нэмэлт зардал

* Аль хэдийн шийдсэн: `serve_d2_merged` (`run_plan_l4.sh:45-64`) нь нэгтгэсэн fp16 жинг ашигладаг. `--enable-lora`
  ашиглавал T4 дээр ~3 дахин удаашрах нь хэмжигдсэн (C1 22.7 с, A1 7.4 с). `--max-lora-rank 64` (`serve_model.sh:49`) нь
  rank-ийн дээд хязгаараар санах ой нөөцөлдөг тул D2/D3 (r = 32) үед `--max-lora-rank 32` болгоход бага зэрэг хэмнэнэ.
  Гэхдээ merge хийх нь илүү сайн тул **өөрчлөх шаардлагагүй**.
* Reproducibility: A100-ийн dev (bf16 + LoRA) ба T4 (fp16, нэгтгэсэн) хооронд аль хэдийн зөрүү бий (WORKLOG:457-460).
  Тайланд энэ хэвээр тэмдэглэгдсэн.

### 2.7 Quantization (T4-д хүчинтэй сонголт)

| Арга | T4 (sm75) дээр | Жин | Тэмдэглэл |
|---|---|---|---|
| FP8 (W8A8 / `--quantization fp8`) | **Үгүй** (Ada/Hopper шаардлагатай) | — | `models.yaml`-ийн L4-ийн sqrl FP8-ийг T4 дээр давтах боломжгүй |
| BF16 | Үгүй | — | fp16 (`--dtype half`) |
| AWQ int4 (+ Marlin kernel) | Тийм. Одоогийн vLLM баримтад Turing-д AWQ, GPTQ, Marlin (GPTQ/AWQ) ✅ гэж байна (MXFP4 үгүй). Хуучин хувилбаруудад Marlin нь sm80 шаарддаг байсан | ~5.5 GB | Хувилбараас хамаарна, баталгаагүй |
| GPTQ int4/int8 | Тийм | 5.5 / 8.5 GB | — |
| bitsandbytes nf4 (in-flight) | Тийм | ~5.5 GB | vLLM дээр AWQ/GPTQ-аас удаан, тохируулга шаардахгүй |
| GGUF | Тийм | — | vLLM дээр туршилтын шатанд |

* **Ашиг.** int4 жин нь (а) GPU тус бүрт 1 replica (§2.5), (б) KV-д 2–3 дахин их зай олгоно. Decode нь санах ойн зурвасаар
  хязгаарлагддаг тул хурдасна. Харин манай 20k prefill нь тооцооллоор хязгаарлагддаг тул W4A16 kernel (dequant + fp16 GEMM)
  prefill-д хурдасгахгүй, бүр удаашруулж ч болно. Нийт хурдасгалт **1.2–1.8 дахин** (баталгаагүй, ихэнх нь replica-аас).
* **Нарийвчлалын зардал.** Kurtic et al. (2025): W4A16 (GPTQ/AWQ) нь нарийвчлалын ~98–99%-ийг хадгалдаг ч 7–8B загвар,
  урт reasoning болон код үүсгэх даалгаварт алдагдал илүү их байдаг. Манай EX-ийн 95%-ийн итгэлийн интервал ±5–6 хувь
  тул 1–3 хувийн алдагдал илрэхгүй ч гэсэн бодитоор оршиж болно. Манай нэгтгэсэн D2 жинг **өөрсдөө quantize**
  хийх шаардлагатай (AWQ/GPTQ: Lin et al., 2024; Frantar et al., 2023). Энэ нь шинэ сан суулгах, манай prompt дээр
  тохируулах (calibration) Kaggle цаг шаардана. Qwen-ийн бэлэн `Qwen2.5-Coder-7B-Instruct-AWQ` нь Arctic/D2 биш тул тохирохгүй.
* **Reproducibility.** Өндөр эрсдэлтэй: загварын жин өөр тул шинэ `served` нэр, шинэ суурь run шаардлагатай. Одоогийн fp16
  run-уудтай шууд харьцуулах боломжгүй. **Дипломын хугацаанд санал болгохгүй.** Хэрэв хийвэл зөвхөн «хурд-нарийвчлалын»
  тусдаа туршилт болгоно.

### 2.8 Speculative decoding / n-gram prompt lookup

* **Санаа.** Draft токеныг prompt-оос n-gram тааруулж санал болгоод, үндсэн загвар нэг forward-оор шалгана
  (Leviathan et al., 2023; Saxena, 2023). SQL нь schema-ийн хүснэгт/баганын нэрийг prompt-оос шууд хуулдаг тул таарах
  магадлал өндөр. Гэвч `<think>` доторх чөлөөт англи текстэд бага.
* **Тохиргоо (баталгаагүй).** `--speculative-config '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_min":2,"prompt_lookup_max":5}'`
  (vLLM-ийн n-gram баримт бичиг). Хуучин хувилбарт `--speculative-model [ngram] --num-speculative-tokens ... --ngram-prompt-lookup-max ...`
  гэж бичигддэг байсан.
* **Хурдасгалт.** Ганц хэрэглэгчтэй web demo (batch 1–2) дээр decode **1.2–1.6 дахин** хурдасна (баталгаагүй). Eval-д
  (batch 8–64, prefill-д дарагдсан) **≈ 1.0 дахин** байх бөгөөд batch том үед бүр удаашруулж болно. Prefill-ийг огт
  багасгахгүй. Мөн гогцоо (§2.9) нь n-gram давталт тул **гогцоог хурдан үүсгэнэ** (давуу тал биш).
* **Нарийвчлал/Reproducibility.** Greedy-д онолын хувьд ижил гаргалт гарна. Sampling-д rejection sampling нь тархалтыг
  хадгалдаг ч seed-ийн дараалал өөрчлөгдөнө: `n = 8` түүвэр өөр гарах тул E2-ийн мөрүүдийг давтах боломжгүй. **Eval-д бүү
  ашигла**, зөвхөн web-д.

### 2.9 Reasoning-ийн уртыг багасгах (`<think>` budget, эрт зогсоох) — **хамгийн өндөр өгөөжтэй**

Arctic-R1-ийн prompt өөрөө «[Limited by 4K tokens]» гэж заадаг (`llm/prompts.py:223`) ба prefill нь
`"Let me solve this step by step.\n<think>"` (`prompts.py:230`). Greedy-д 17% нь 3072-д тулж тасардаг (§0.2).

* **(a) `max_tokens` 3072 → 1536** (`config/models.yaml:14`). Тасраагүй гаргалтын 99% нь < 1 000 токен. H4-ийн Σ completion
  253k → ~173k (**−32% decode**). KV-ийн дундаж хэрэглээ буурч, зэрэг дарааллын тоо нэмэгдэнэ. Нэг үүсгэлттэй run
  **10–20%**, E2 **20–35%** хурдасна (баталгаагүй). Нарийвчлалын эрсдэл: 3072-д тасарсан ч зөв гарсан 15 асуулт
  (SQL нь гогцооноос өмнө гарсан ```sql блокоос авагдсан байх магадлалтай) 1536-д мөн зөв үлдэх эсэх нь **тодорхойгүй**.
  Шалгах хямд арга: тасарсан 52 асуултаар (`completion_tokens ≥ 3000`) `max_tokens` 1536-тай жижиг run хийх (~5 мин;
  `config/models.yaml`-ийн загварын `max_tokens`-ээр — `t2s eval`-д `--max-tokens` сонголт, RunOptions-д `max_tokens` талбар алга).
* **(b) Budget forcing** (s1, Muennighoff et al., 2025). Гаргалт `finish_reason = "length"`-ээр тасарвал
  `"…\n</think>\n<answer>\n```sql\n"`-ийг prefill болгон залгаж (`client.py:67-70`-ийн `continue_final_message` бэлэн байгаа),
  ~200 токеноор SQL-ийг «шахаж» гаргуулна. Угтвар нь prefix cache-д байгаа тул нэмэлт зардал бага (~5%). Тасарсан 17%-ийн
  зөв хувийг (29%) богино гаргалтынх (39%) руу ойртуулах боломжтой: **+0–3 хувь EX** (баталгаагүй, dev-д хэмжих). Энэ нь
  хурд **ба** нарийвчлалын аль алинд ашигтай цорын ганц арга.
* **(c) Гогцоог эрт илрүүлэх.** Streaming + клиент талд n-gram давталт (жишээ нь сүүлийн 200 токенд 30 токены хэсэг ≥ 3 удаа
  давтагдвал) илэрвэл тасалж, (b)-г хэрэгжүүлэх. Илүү нарийн боловч клиентийн өөрчлөлт ихтэй. `repetition_penalty` /
  `frequency_penalty` нь бүх гаргалтын тархалтыг өөрчилдөг тул **reproducibility-д муу** (шинэ суурь шаардана).
* **(d) vLLM-ийн `thinking_token_budget`.** Шинэ хувилбаруудад нэмэгдсэн гэх мэдээлэл бий (vLLM forum, хэрэглэгчийн тайлбар).
  Arctic-д reasoning parser ашигладаггүй тул (`serve_model.sh:9`) тохирох эсэх нь баталгаагүй. (b)-г клиент талд хийх нь
  хувилбараас хамаарахгүй.
* **Reproducibility.** `max_tokens` нь `options_hash`-д ордоггүй тул (§0.5) **шинэ run ID** (жишээ нь `H4b1536`) болгож,
  resume-ийг хольж болохгүй. Budget forcing нь шинэ сонголт тул fingerprint-д автоматаар орно (options-ийн талбар болгосон
  тохиолдолд).

### 2.10 Бүх асуултыг нэг дор batch хийх

* Одоо `workers` thread тус бүр нэг асуулт → нэг HTTP хүсэлт (`n` түүвэртэй) илгээдэг. vLLM-ийн continuous batching нь
  хүсэлтүүдийг GPU дээр нэгтгэдэг тул «бүх 300 асуултыг нэг offline `LLM.generate`-д» шилжүүлэх нь T4 дээр KV-ийн хязгаараас
  болж бага ашиг өгнө (**0–10%**, баталгаагүй). Харин SQL гүйцэтгэх, засвар хийх зэрэг CPU/DB-ийн хэсэг GPU-тэй давхцахгүй
  болж, GPU сул зогсох нь нэмэгдэнэ.
* Илүү бодит арга: **хоёр үе шаттай eval** — (1) бүх асуултын эхний үүсгэлтийг өндөр `workers`-тэй хийж кэшлэх, (2) гүйцэтгэл,
  засвар, санал хураалтыг дараа нь хийх. Засвар нь өөрөө LLM дуудлага тул бүрэн салгах боломжгүй.
  `repair_workers` (`options.py:33`) > 1 нь засварын дараалсан гинжийг зэрэг ажиллуулж, E2-ийн p95-ыг бууруулна (hash-д
  ордоггүй, гаралт ижил гэж тайлбарласан).

### 2.11 Run хооронд ижил prompt-ийг кэшлэх

* **Ажиглалт.** Олон run нь яг ижил хүсэлтийг давтдаг. E1 = H4 + засвар тул эхний greedy үүсгэлт нь H4-тэй ижил prompt,
  `temperature = 0`, ижил `max_tokens` байна. Засвартай нь зөвхөн 41/300. E4/E4c/E4f/E5h нь аль хэдийн E2-ийн хувилбаруудыг
  офлайн дахин сонгодог (`eval/reselect.py`, `ensemble_offline`) нь энэ санааны амжилттай жишээ.
* **Санал.** Клиент түвшний диск кэш (`OpenAICompatLLM.chat`): түлхүүр = sha1(served model + model_revision + бодит vllm args +
  messages + prefill + n + temperature + top_p + max_tokens + seed + stop), утга = choices + usage. `results/cache/llm/*.jsonl`-д
  хадгалж Kaggle-ийн Output/Input-ээр сесс хооронд дамжуулна. Ингэснээр E1-ийн зардал ~**15–20%** болж буурна (зөвхөн засвар).
  Ижил prompt-той шинэ сонгогч/санал хураалтын туршилтууд (vote_filter, abstain босго, дүрэм) GPU огт шаардахгүй.
* **Reproducibility.** Эерэг нөлөөтэй: fp16 vLLM нь batch-ийн бүрэлдэхүүнээс хамаарч bit-түвшинд детерминист биш тул кэшээс
  тоглуулах нь яг ижил гаргалтыг баталгаажуулна. Нөхцөл: кэшийн файлын sha1-ийг meta-д бичих, кэшээс авсан мөрийг
  тэмдэглэх (`cache_hit`), хурдны хэмжүүрийг (`gen_ms`) кэшгүй run-аас авах.

## 3. Reproducibility-ийн тусгай анхааруулга (run hash)

1. `runner.py:435`: `vllm_args` нь `models.yaml`-аас бичигддэг. T4 дээр бодит `T2S_VLLM_ARGS`(+`__<нэр>`), GPU-ийн нэр
   (`nvidia-smi`), vLLM-ийн хувилбарыг бичихгүй байна. Аль ч §2-ын өөрчлөлтөөс **өмнө** эдгээрийг meta-д нэмэх хэрэгтэй.
2. `options_hash` (`runner.py:289-293`) = options + served + variant + seed + eval_set. `max_tokens`, `vllm_args`, `workers`
   ордоггүй. §2.3/§2.9-ийн өөрчлөлтийг **шинэ `--tag`** эсвэл шинэ run ID-аар ажиллуулж, хуучин jsonl-д resume хийхгүй байх.
3. `requirements-gpu.txt` нь `vllm`-ийг түгжээгүй тул Kaggle сесс бүрт өөр хувилбар суух боломжтой. Prefix caching-ийн анхдагч,
   Turing-ийн attention backend, Marlin-ийн дэмжлэг зэрэг нь хувилбараас хамаарна. Эцсийн тайлангийн run-уудад хувилбарыг
   түгжих (D3-ийнх шиг) санал болгоно.
4. Хурдны аливаа өөрчлөлт greedy гаргалтыг fp16-ийн тоон дарааллаар бага зэрэг өөрчилж болно. Тиймээс «зөвхөн хурдны»
   өөрчлөлтийн дараа H4-ийн 300 асуултаар нэг удаа шалгаж, `correct`-ийн зөрүүг McNemar-аар (одоогийн тайлангийн арга)
   тайлагнах нь зүйтэй.
